## Главное коротко

1. **Это рабочий, большой и во многом доделанный продукт, но граф в нём — только часть.** 1069 коммитов с 2026-03-26 по 2026-06-24, версия 3.0.0. Rust — около 135 тыс. строк (с тестами), плагины Unreal — около 199 тыс. строк C++/Python, из них 167 тыс. — чужой форк Copilot. Кроме графа там миграция Blueprint→C++, трекер миграции в Obsidian, локализация, «команды агентов», инструменты для редактора. **[код]**
2. **Стек ядра подходит нам почти один в один, если ядро будет на Rust.** Это один бинарь `xray.exe` (CLI + MCP по stdio + HTTP-мост), `rusqlite` с встроенным SQLite и FTS5, `rmcp` 1.x (официальный Rust SDK для MCP), `tree-sitter` 0.24, `rayon`. Всё это собирается и работает под Windows с Claude Code. Для F03-02 это готовое доказательство, что путь «Rust + rmcp + SQLite» жизнеспособен. **[код]** `Cargo.toml`, `crates/xray-mcp/Cargo.toml`
3. **Граф устроен в два слоя, и эту идею стоит взять.** Нижний слой — «сырые факты»: вызов записан с текстовыми именами вызывающего и вызываемого и с id цели, если её удалось найти. Верхний слой — таблица `graph_edges`, которую целиком пересобирают SQL-запросами из фактов. Факт без разрешённой цели не теряется, но и в граф не попадает. Это совпадает с решением К3 из ADR-001. **[код]** `crates/xray-core/src/db.rs:8042` (`build_graph_edges`), `db.rs:7325` (`insert_cpp_call`)
4. **Но узлы адресуются целочисленными id, а это источник целого класса ошибок.** Используются `INSERT OR REPLACE`, внешние ключи, которые при массовом импорте выключены, и FTS-строки со сдвигом `rowid` (+1 млн на каждый тип). В аудите и статусе — длинная серия ошибок «осиротевшие строки», «нарушение внешнего ключа», «потеря рёбер при пересборке». У нас узел должен иметь стабильный строковый ключ (`путь#Класс.метод`, GUID). **[код]** `db.rs:6258`, `db.rs:8544`; `docs/plans/bright-dancing-dove.md`, `docs/status-2026-05-29.md` §7
5. **Граф вызовов C++ видит только функции с макросом `UFUNCTION`.** Узлы-функции создаёт только построчный разбор макросов в заголовках. Обычные методы C++ и классы без `UCLASS` узлами не становятся. Их вызовы лежат в `cpp_call_edges` с текстом, но в граф не попадают. Для Unreal это осознанный выбор («что видно из Blueprint»), для C# в Unity так делать нельзя. **[код]** `crates/xray-cpp/src/ue_macros.rs:410-470`, `db.rs:8110-8117`
6. **Разрешение вызовов по уровням L1–L6 — хороший образец для C#.** L1 — `Foo::Bar()`, L2 — вызов без квалификатора как метод своего класса, L3 — `Super::` через родителя, L4 — аргумент шаблона, L5 — тип локальной переменной, параметра или поля, L6 — `Delegate.Broadcast()` → ребро «транслирует делегат». Обход дерева tree-sitter с картой локальных типов на каждую функцию переносится на `tree-sitter-c-sharp` почти механически. Недостаток: разрешение идёт в момент вставки, отдельным `SELECT` на каждый вызов, и поэтому зависит от порядка. **[код]** `crates/xray-cpp/src/call_graph.rs`, `db.rs:7325-7470`
7. **Blueprints и ассеты читаются только изнутри движка.** Плагин-commandlet `XRayDump` запускает редактор без окна, обходит ассеты через рефлексию и пишет JSON: по файлу на Blueprint и граф зависимостей ассетов. Rust импортирует этот JSON в SQLite. Для Unity этот путь не нужен: там YAML текстовый (отчёт 05). Для будущей F-11 плагин `XRayDump` — готовый код целиком. **[код]** `plugin/XRayDump/Source/XRayDump/Private/*`, `crates/xray-core/src/import.rs`
8. **Инкрементальность есть, но неполная.** Для C++ проверяются время изменения файла и хэш содержимого. Перечитываются только изменённые файлы, но производные таблицы (наследование, `graph_edges`, FTS) каждый раз пересобираются целиком. Для ассетов есть кэш дампа по времени изменения и версии формата, выборочный импорт и слежение в редакторе с задержкой 2 с. Свежесть для агента определяется по возрасту индекса («старше часа»), а не по изменённым файлам. Сторож файлов (watcher) спроектирован, но не сделан. **[код]** `crates/xray-cpp/src/lib.rs:249-280, 651-770`, `crates/xray-core/src/completeness.rs:31`; **[docs]** `docs/superpowers/specs/sprint-auto-rebuild-triggers.md`
9. **Главная ошибка — рост «вширь»: таблица, импортёр и MCP-инструмент на каждый тип ассета.** Получилось 121 `CREATE TABLE`, 110 миграций схемы, 127 MCP-инструментов, `db.rs` на 14,8 тыс. строк с ~406 методами, `main.rs` на 13,5 тыс. строк. Потом пришлось сворачивать инструменты в фасады `xray_query`/`xray_list`: по коду по умолчанию скрыт 41 инструмент, видно около 86, в docs сказано «~69». Для Unity нужен общий граф «узел с видом + рёбра + свойства в JSON», а не таблица на тип. **[код]** `crates/xray-core/src/db/schema.rs`, `crates/xray-mcp/src/server.rs:152-243`
10. **Слой MCP стоит взять почти кодом.** В нём есть: кэш открытых БД с переоткрытием, когда файл БД изменился на диске; параметр `project` для нескольких проектов и поиск `xray.db` вверх от текущей папки; инструкция агенту в `initialize`; пометки `read_only_hint`; отдельный профиль без пишущих инструментов; единый формат ответа «не найдено»; постраничная выдача с флагом `truncated`; рецепты запросов как MCP-ресурсы. **[код]** `crates/xray-mcp/src/server.rs`, `project.rs`, `tools.rs:179-204`
11. **Крейт `xray-vault` — готовый код для знаний проекта в Markdown (F-07/F-08).** В нём: стабильный id записи (BLAKE3 от исходного пути, переживает переименование), атомарная запись через `.tmp` + `rename` с учётом Windows, авто-секция между маркерами при сохранении ручного текста, белый список «наших» ключей frontmatter, канонический хэш для пропуска неизменённых файлов, файл состояния в git, проверка версии схемы. Перед переносом нужно применить исправления из аудита: блокировка без гонки, обрезка имени по границе символа, экранирование переводов строк в YAML. **[код]** `crates/xray-vault/src/*`; **[docs]** `docs/audit-2026-05-29.md` M8–M11
12. **Документы отстают от кода, и это повторять нельзя.** Сам статус 2026-05-29 признаёт, что десятки пунктов с `[ ]` и `draft` на деле сделаны. `completeness.rs` помечен «не сделан», а в коде он есть. Счётчики инструментов расходятся: 55, 108, 109, ~69 и 127 по коду. `AGENTS.md` — ручная копия `CLAUDE.md`, и она уже разошлась с оригиналом. **[код]/[docs]**

### 1.4. Интеграции с агентами

- **MCP по stdio** — основной путь для Claude Code, Cursor и Codex: `xray mcp [--db]`. Шесть вариантов `.mcp.json`: глобальная установка; бинарь внутри плагина по относительному пути; абсолютный путь; явная БД; путь через переменную окружения; монорепозиторий. Без `--db` сервер ищет `xray.db` вверх от текущей папки, как git ищет `.git`. **[код]** `.mcp.json.example`, `crates/xray-mcp/src/project.rs:78`
- **HTTP-мост `xray serve`** (127.0.0.1:8923, только чтение) — для встроенного агента UE 5.8 через `MCPClientToolset`. Пишущие инструменты из этого профиля вырезаются. **[код]** `server.rs:218-223, 271-290`; **[docs]** `docs/xray-3.0-native-integration.md`

**Приёмы слоя MCP (все [код]):**
- Инструкция агенту в ответе `initialize`: порядок «search → query → context/hierarchy/impact», какие инструменты пишут, «индекс — снимок, проверь свежесть» (`server.rs:646-660`).
- Рецепты запросов (`docs/query-cookbook.md`, 969 строк) отданы как **MCP-ресурсы** `xray://cookbook/<глава>`, а не зашиты в описания инструментов. Есть MCP-prompt `xray_ask` (`server.rs:472-520`).
- Кэш открытых БД по каноническому пути. Если время изменения файла БД сдвинулось (внешний `xray rebuild`), БД переоткрывается. Счётчики попаданий и переоткрытий видны через `xray_diagnostics` (`server.rs:12-440`).
- Единый ответ «не найдено» в JSON: `{found:false, entity_type, name, message}` (`tools.rs:191`).
- Постраничная выдача: `limit` по умолчанию 200, не больше 500, флаг «есть ещё» (`tools.rs:179`). В аудите отмечено, что применяется не везде.
- Пометки `read_only_hint`, `open_world_hint` на инструментах.

## 2. Индексация: что читается, как, инкрементально ли, сколько времени

### 2.1. C++

**Заголовки (`.h`, `.hpp`) — построчный разбор без tree-sitter.** Ищутся строки, начинающиеся с `UCLASS(`, `UINTERFACE(`, `USTRUCT(`, `UENUM(`, `DECLARE_*DELEGATE*`. Текст макроса собирается по скобкам через несколько строк. Следующая строка считается объявлением (`class X_API AFoo : public ABar, public IBaz`). Тело класса собирается по фигурным скобкам. Внутри тела ищутся `UFUNCTION(` и `UPROPERTY(` на верхнем уровне (вложенные классы с исправления M4 пропускаются). Спецификаторы (~311 видов) разбираются в типизированные структуры и сохраняются JSON-колонкой `parsed_specifiers`. **[код]** `crates/xray-cpp/src/parser.rs`, `ue_macros.rs:1-120, 410-500`, `crates/xray-core/src/specifier_types.rs`

Следствие: узлы-функции и узлы-свойства появляются **только** для членов с `UFUNCTION`/`UPROPERTY`. Классы — только с `UCLASS`/`USTRUCT`/`UINTERFACE`. Обычный C++ в граф как узлы не попадает. Кроме того, `IFoo` у `UINTERFACE` не разбирается: в коде стоит `TODO(S5a)` (`ue_macros.rs:72-82`). **[код]**

**Исходники (`.cpp`) — tree-sitter.** Три функции — `extract_calls`, `extract_property_accesses`, `extract_includes` — каждая заново разбирает файл. Тройной разбор — находка аудита M5. Она не исправлена: в `lib.rs:153` об этом стоит комментарий. Обход устроен так **[код]** (`call_graph.rs`):
- на входе в `function_definition` берётся квалифицированное имя (`AFoo::Bar`) и **новая** карта «имя переменной → тип» из параметров и локальных объявлений (`auto` пропускается);
- `call_expression` разбирается по четырём формам: `Foo::Bar()`, `obj->M()`/`obj.M()` (тип `obj` — из карты), `M()`, `Foo<T>()`;
- макросы отсекаются чёрным списком (`TEXT`, `UE_LOG`, `check`, `Cast`…) и правилом «ВСЁ_ЗАГЛАВНЫМИ»;
- типы очищаются от `TObjectPtr<>`, `TWeakObjectPtr<>`, `TSubclassOf<>`, `*`, `&`, `const`.

**Разрешение вызова в цель** идёт при вставке в БД, отдельными `SELECT` (`db.rs:7325-7470`) **[код]**:

| Уровень | Что | Как |
|---|---|---|
| L1 | `Foo::Bar()` | точный поиск `qualified_name` |
| L2 | `Bar()` без объекта | пробуем `КлассВызывающего::Bar` |
| L3 | `Super::Bar()` | родитель из `ue_classes.parent_name` |
| L4 | `CreateDefaultSubobject<UComp>()` | аргументы шаблона сохраняются JSON |
| L5 | `obj->Bar()` | сначала локальная карта типов (при разборе), затем тип `UPROPERTY` класса вызывающего (при вставке) |
| L6 | `OnDeath.Broadcast()` | при сборке рёбер: объект → свойство → тип-делегат → ребро `broadcasts` |

Нашлась цель — `callee_function_id` заполнен. Не нашлась — строка остаётся с текстом `callee_name`/`callee_qualified_name`, но в `graph_edges` не попадает. Угадывания по «единственному имени в проекте» нет: это совпадает с правилом Graft из ADR-001. **[код]**

**`.Build.cs`** — модуль и его зависимости `PublicDependencyModuleNames`/`PrivateDependencyModuleNames`. Класс относится к модулю по ближайшему вверх `.Build.cs`. Модули из `Plugins/` помечаются `source_type = plugin`. **[код]** `build_cs.rs`, `lib.rs:514-610`

Файлы читаются параллельно через `rayon`. Папки `Binaries`, `Intermediate`, `Saved`, `DerivedDataCache`, `.git`, `.vs`, `node_modules` пропускаются. BOM удаляется. **[код]** `lib.rs:24-50, 90-150`

## 3. Модель графа

### 3.1. Узлы

Отдельного «узла» нет. Узел — это строка в одной из таблиц сущностей: `ue_classes` (`kind`: class/struct/interface), `ue_functions`, `ue_properties`, `ue_delegates`, `ue_enums`, `ue_modules`, `blueprints`, `assets`, `config_entries`, `data_tables`, `data_assets` и десятки таблиц подсистем. Адрес узла в графе — пара `(source_type, source_id)`, где `source_id` — автоинкрементный `INTEGER PRIMARY KEY` своей таблицы. **[код]** `db/schema.rs`, `db.rs:8042`

Уникальность держится на именах. Для функций — `UNIQUE(qualified_name)` (`schema.rs:46`). Классы ищутся по `name` (`db.rs:8012`), то есть опора на правило UE «имя класса уникально в проекте». Для C#, TS и Go это не так.

### 3.2. Рёбра

Одна таблица `graph_edges(source_type, source_id, target_type, target_id, edge_type, metadata JSON, UNIQUE(...))` с индексами по источнику, цели и типу. **[код]** `docs/ue-xray-spec.md` §6, `db.rs:8042-8530`

| Группа | Типы рёбер |
|---|---|
| Структура C++ | `inherits`, `has_function`, `has_property`, `depends_on` (модули) |
| Код C++ | `calls`, `reads`, `writes` (метаданные: файл и строка), `broadcasts` (делегат) |
| C++ ↔ BP | `bp_inherits_class`, `bp_inherits_bp`, `bp_calls_function`, `bp_reads_property`, `bp_writes_property`, `bp_implements_interface`, `bp_widget_binding` |
| BP ↔ BP | `bp_calls_bp`, `bp_casts_to`, `bp_spawns`, `bp_creates_widget`, `bp_references` |
| Данные | `asset_depends_on`, `config_overrides`, `dt_references`, `da_references`, `state_transitions_to` и рёбра подсистем |

У рёбер **нет** пометки источника или уверенности. Всё, что в графе, считается точным, неразрешённое лежит в таблицах фактов. **[код]**

### 3.3. Хранение

- SQLite (`rusqlite` bundled) в режиме WAL, `busy_timeout=5000`, `journal_size_limit=32 МБ`, `foreign_keys=ON` (при массовом импорте выключаются). Один файл `xray.db` в корне проекта. **[код]** `db.rs:400-420`
- 121 `CREATE TABLE`, 110 констант миграций, таблица `schema_version`. Если БД новее бинаря, открытие отказывает. Миграции «добавить колонку» идемпотентны: ошибка `duplicate column name` глотается, остальные пишутся в лог. Раньше глотались все 18 — это находка аудита M12. **[код]** `db/schema.rs`, `db.rs:302-395`
- Факты и производные данные разделены:
  - факты — `cpp_call_edges`, `cpp_property_access`, `cpp_includes`, `bp_function_calls`, `bp_property_access`, `bp_graph_nodes`…, с текстовыми именами и nullable id цели;
  - производные — `ue_inheritance` (транзитивное замыкание рекурсивным CTE), `graph_edges`, `xray_search` (FTS5).
  Производные пересобираются `DELETE` + `INSERT … SELECT`. **[код]** `db.rs:8023-8640`
- FTS5 — обычная (не contentless) таблица `xray_search(name, qualified_name, entity_type, file_path, module)`. `rowid` = id + 1 000 000 × номер типа (классы 0, функции +1 млн, свойства +2 млн, …). Для BP, DataTable, DataAsset есть точечное обновление по путям, чтобы не перестраивать ~50 тыс. строк. **[код]** `db.rs:8544-8740`
- Сжатие после импорта (`compact_after_import`): checkpoint WAL, при большом «мусоре» — `VACUUM`. **[код]** `db.rs:8744`

### 3.4. Запросы

| Запрос | Как устроен | Где |
|---|---|---|
| Найти сущность по имени | Цепочка проб: функции по `qualified_name` → классы по `name` → BP по имени или пути → свойства → делегаты → перечисления; первое совпадение выигрывает | `impact.rs:13` (`resolve_entity`) |

### 3.5. Слабые места модели

1. **Целочисленные id как адрес узла.** Пересоздание строки (`INSERT OR REPLACE`) даёт новый id, и старые ссылки из фактов, рёбер, FTS и памяти агента «уезжают». Сервер даже подсказывает агенту: после внешней пересборки «запомненные id могут указывать на другие строки» (`server.rs:55-60`). **[код]**
2. **Таблица на каждый вид сущности.** `resolve_entity`, `resolve_entity_name`, `build_fts_index` и `build_graph_edges` — длинные `match` по видам. Каждый новый вид ассета — правка в 5–7 местах. **[код]**
3. **Разрешение вызовов при вставке** — `SELECT` на каждый вызов и зависимость от порядка вставки. Правильнее: собрать все объявления, потом одним проходом разрешать в памяти. **[код]**
4. **Производные таблицы пересобираются полностью** на каждом обновлении. На масштабе UE-проекта это терпимо, для частых обновлений из хука после правки — нет. **[код]**
5. **Нет меток источника и уверенности на рёбрах** (сравни ADR-001 §1 «две метки на каждом ребре»). **[код]**
6. **Опора на уникальность коротких имён**: классы по `name`, BP в дампе по короткому имени. Аудит H6: два `BP_Door` в разных папках затирали друг друга. **[docs]** `docs/audit-2026-05-29.md` H6

**Почему что-то не доделано** (мой вывод по документам и истории коммитов):
- **расползание рамок**: к графу добавились миграция BP→C++, Obsidian-трекер, локализация через ИИ, «команды агентов» (`crew_*`), форк коммерческого копилота, инструменты для нативного AI-стека UE 5.8. Графу и его свежести внимания досталось меньше, чем подсистемам;
- **подход «инструмент на подсистему»** давал быстрый видимый результат, но каждая подсистема добавляла таблицу, импортёр и инструмент, которые потом надо было проверять (51 задача аудита);
- **документы не успевали за кодом**: галочки `[ ]` при готовом коде, пять разных счётчиков инструментов.

## 5. Сильные стороны

1. **Один нативный бинарь без рантайма**: ни Python, ни Node, ни демона для основного режима. Ставится копированием, работает на Windows. Это прямо то, что требует ADR-001 §7 («установка одной командой»). **[код]**
2. **Разделение «факты → производный граф»** с сохранением неразрешённого. **[код]**
3. **Честность ответа**: единый «не найдено», сводка полноты данных («C++ разобран, BP не импортированы — запусти дамп»), предупреждение об устаревании, флаг `truncated`. **[код]** `completeness.rs`, `tools.rs:191`
4. **Постепенная выдача**: `xray_search` → `xray_query` → `xray_context` (сначала счётчики, потом разделы), `tier=overview`. Это наши L0/L1/L2. **[код]**
5. **Доменный риск в последствиях правки**: не только «кто зависит», но и «почему опасно» (RPC, репликация, число BP-вызывающих). **[код]** `impact.rs`
6. **Правила проекта на SQL** с защитой «только чтение». **[код]** `rules.rs`
7. **Аккуратная работа с файлами пользователя** в `xray-vault`: атомарная запись, маркеры, сохранение ручного текста, стабильный id при переименовании, версия схемы, файл блокировки. **[код]**
8. **Устойчивость к падениям внешнего процесса**: запись «что сейчас делаю», список пропусков, повтор. **[код]** `dump.rs`
9. **Много тестов** (1385) и привычка к состязательному аудиту: находка → проверка отдельным агентом → исправление. **[docs]**

## 8. Что это значит для решений архитектуры

- **[[F03-01 Своё ядро или готовый движок]].** ue-xray — не готовый движок для нашего стека: он заточен под UE, модель данных «таблица на вид», C# и Unity нет. Но из него можно поднять **каркас своего ядра на Rust**: бинарь, SQLite, MCP-слой, инкрементальный сканер, CTE для последствий, `xray-vault` для Markdown. Писать с нуля пришлось бы примерно то же.
- **[[F03-02 Язык ядра и способ поставки]].** Довод за Rust: у нас уже есть рабочий опыт. `rmcp` 1.x держит stdio и Streamable-HTTP, `rusqlite` bundled с FTS5 собирается в один `.exe`, `tree-sitter` 0.24 работает с грамматиками. Известные грабли: debug-сборка на Windows падала от переполнения стека; `rmcp` сам не делит `tools/list` на страницы; для клиентов старых версий приходится закреплять версию протокола (`server.rs:30-36`).
- **[[F03-03 Хранение индекса и знаний]].** Подтверждение ADR-001: SQLite + FTS5 + таблица рёбер + рекурсивные CTE достаточно, графовая БД не нужна. Поправки: ключи — строки; неразрешённые ссылки — отдельная таблица с кандидатами; рёбра с пометкой источника; не держать тяжёлые сырые данные (граф нод BP) в той же БД, что и граф ссылок, если они не нужны для ответов — у GrandHustle БД весила 220–277 МБ.
- **[[F03-04 Интерфейс для агента]].** Прямой опыт «127 инструментов — много» и выход через глаголы. Брать с первого дня: `instructions`, рецепты-ресурсы, «не найдено» одной формой, `truncated`, сводку полноты.
- **[[F-11 Поддержка Unreal]].** Когда до неё дойдёт: взять `XRayDump` как есть и импортировать его JSON в нашу общую модель. Разбор C++ — через общий модуль C++ на tree-sitter плюс модуль «UE-макросы» как надстройку, а не отдельный построчный парсер.

## 9. Что не проверено и что проверить

1. Не собирал и не запускал: работоспособность и скорость — со слов документов.
2. Как инкрементальное обновление C++ ведёт себя, если меняется заголовок, а вызывающие `.cpp` не меняются: остаются ли «висячие» `callee_function_id` или срабатывает внешний ключ. По коду повторного разрешения не видно. Нужен тест, если будем переносить сканер.
3. Сколько MCP-инструментов реально видит клиент: по коду ~86, в docs ~69.
