## Главное коротко

1. **Q00: решение о приёмке принимают только реально выполненные команды, а не LLM.** Три ступени есть, но работают не так, как в рекламе. Ступень 1 (линтер, сборка, тесты) — единственная, которая может *одобрить*. Ступени 2 и 3 (LLM-оценка и голосование моделей) могут только *задержать* одобрение и дать отзыв. Если ни одна команда не выполнилась, итог — «не проверено», а не «принято». Это самый ценный приём для нашей будущей проверки перед слиянием.
2. **Q00: исполнитель не видит проверочную команду и ожидаемый вывод.** В коде это поля `verify_command` и `output_assertion`. Их вырезают из текста задачи для исполнителя и из подсказок при повторе. Команду запускает оркестратор после исполнителя, а не сам исполнитель. Слабое место признают сами авторы: вырезание идёт по точному тексту, так что пересказанную или перекодированную копию фильтр не поймает.
3. **Q00: журнал событий — обычная таблица SQLite «только добавлять»** с полями тип, агрегат, время и JSON-данные. Из неё восстанавливают состояние. Идея простая и нам подходит. Код брать не стоит: 3100 строк, и почти все они про гонки между процессами.
4. **razzant: ревью делает отдельный агент по «замороженному» диффу.** Этот агент ничего не правит и отвечает JSON-чек-листом на 8 пунктов. Если ревью не удалось провести, это честно помечается `NOT_RUN`, а не выдаётся за чистый результат. Внутри агента то же устроено как конвейер `commit_reviewed`: предварительное ревью → три модели по диффу и параллельно «scope»-ревьюер, который сам читает репозиторий инструментами только для чтения → тесты. Ложится на наш слой «проверка» почти один в один, а наша карта кода даёт ревьюеру то, что razzant собирает вручную.
5. **razzant: `--memory-mode forked` — задача работает на копии памяти.** Копируются identity/WORLD/registry и знания. Всё, что задача узнала, выгружается отдельным файлом `memory_export.json` и **никогда не сливается в общую память автоматически**. Для нас это готовая схема: «личный черновик задачи → явное предложение в общие знания».
6. **razzant: результат задачи — патч и манифест к нему.** Патч `workspace.patch` строится против базового коммита. В манифест `workspace_patch.json` попадают причины исключений: секреты, мусор, lock-файлы без изменения манифеста. Но это запись изменений, а не песочница: агент правит рабочую папку напрямую.
7. **razzant: долговременная память — это markdown-файлы с журналами.** Черновик ограничен 10 блоками, вытесненное уходит в журнал. Знания хранятся как темы с оглавлением. Есть реестр паттернов, который пополняется после задач. Для каждого проекта заведено отдельное хранилище фактов. Всё рассчитано на одного владельца, командного обмена через git нет.

## Q00/ouroboros

### Приём Q1. Трёхступенчатая проверка (Mechanical → Semantic → Consensus)

**Что это и зачем.** После выполнения задачи результат проверяется по критериям приёмки (AC). Сначала идут дешёвые механические проверки. Потом LLM оценивает смысл. Потом, при сомнениях, голосуют несколько моделей. Цель — не принять работу «на слово».

**Как устроено на самом деле.**

- Конвейер собран в `EvaluationPipeline` — [Q00:src/ouroboros/evaluation/pipeline.py](https://github.com/Q00/ouroboros/blob/40d04413e7e7eef324dc80504d1ce06e11ddd392/src/ouroboros/evaluation/pipeline.py). **[код]**
- **Ступень 1, механическая** — [evaluation/mechanical.py](https://github.com/Q00/ouroboros/blob/40d04413e7e7eef324dc80504d1ce06e11ddd392/src/ouroboros/evaluation/mechanical.py), класс `MechanicalVerifier` (стр. 207). **[код]**
  - Запускает до пяти команд проекта: lint, build, test, static, coverage (порог покрытия 0.7).
  - Команды не зашиты по языкам. Их один раз предлагает LLM, смотря на `package.json`, `pyproject.toml`, `Makefile` и т.п. Каждая предложенная команда сверяется с тем, что реально есть на диске: скрипт в `package.json`, цель в Makefile, бинарник в PATH. Результат сохраняется в `.ouroboros/mechanical.toml`. Всё, что не подтвердилось, помечается `skip`, чтобы не было «фантомных» падений. Код детектора: [evaluation/detector.py](https://github.com/Q00/ouroboros/blob/40d04413e7e7eef324dc80504d1ce06e11ddd392/src/ouroboros/evaluation/detector.py). **[код]**
  - Ступень 1 намеренно не зависит от конкретного критерия: она проверяет, что «проект в целом зелёный». Для нескольких критериев её запускают один раз (инвариант описан в docstring `evaluate`). **[код]**
  - Итог ступени — одно из трёх состояний (`MechanicalDisposition`): `executed_pass` (что-то выполнилось, и всё прошло), `executed_fail`, `no_evidence` (ничего не выполнилось). **[код]**
- **Ступень 2, смысловая** — [evaluation/semantic.py](https://github.com/Q00/ouroboros/blob/40d04413e7e7eef324dc80504d1ce06e11ddd392/src/ouroboros/evaluation/semantic.py). **[код]**
  - Одна LLM возвращает JSON: `score`, `ac_compliance`, `goal_alignment`, `drift_score`, `uncertainty`, `reward_hacking_risk` («результат подогнан под проверяющего, а не решает задачу») и доказательства.
  - Проверяющему (не исполнителю!) показывают «объявленный контракт успеха», включая `verify_command` и `output_assertion` (стр. ~132–150).
- **Ступень 3, консенсус** — [evaluation/consensus.py](https://github.com/Q00/ouroboros/blob/40d04413e7e7eef324dc80504d1ce06e11ddd392/src/ouroboros/evaluation/consensus.py). **[код]**
  - Простой режим: три модели голосуют, нужно 2/3.
  - Совещательный режим (`DeliberativeConsensus`, стр. 715): три роли — адвокат, «адвокат дьявола» и судья, два раунда.
  - Если ключи есть только к одному провайдеру, «консенсус» — это **одна и та же модель с тремя разными системными промптами** (`SINGLE_MODEL_PERSPECTIVES`, стр. 62). Результат честно помечает, в каком режиме шёл консенсус.
  - Ступень запускается не всегда, а по «матрице триггеров»: изменилась спецификация, дрейф > 0.3, неуверенность ступени 2 > 0.3, ручной запрос и др. См. [evaluation/trigger.py](https://github.com/Q00/ouroboros/blob/40d04413e7e7eef324dc80504d1ce06e11ddd392/src/ouroboros/evaluation/trigger.py), `ConsensusTrigger`.
- **Независимость проверяющего** — [evaluation/reviewer_independence.py](https://github.com/Q00/ouroboros/blob/40d04413e7e7eef324dc80504d1ce06e11ddd392/src/ouroboros/evaluation/reviewer_independence.py). Из «жюри» по возможности убирают модели того же вендора, что и исполнитель (не опуская жюри ниже двух голосов). На результат ставится честная метка: `independent`, `same_vendor`, `unverified` или `unavailable`. **[код]**
- **Главное правило приёмки** — функция `decide_final_approval` в [evaluation/models.py](https://github.com/Q00/ouroboros/blob/40d04413e7e7eef324dc80504d1ce06e11ddd392/src/ouroboros/evaluation/models.py) (стр. 566). **[код]**
  - Одобрить может **только** ступень 1 с реально выполненными командами.
  - Любая LLM-ступень может только отказать: несоответствие AC, оценка < 0.8, консенсус не достигнут, риск подгонки ≥ 0.7 (`model_review_withhold_reason`, стр. 526).
  - Одобрение ступени 3 не снимает блок ступени 2.
  - Без выполненных команд итог — `unverified`, даже если все модели сказали «да».
- **Отдельно от конвейера есть «проверочные ворота» критерия** (verify gate). После исполнителя оркестратор сам проверяет, что ожидаемые файлы существуют, затем запускает `verify_command` (код выхода 0, а если задан `output_assertion` — эта подстрока должна быть в выводе). Если команда изменила рабочую папку, это считается провалом. См. `_run_ac_verify_gate` в [orchestrator/parallel_executor.py](https://github.com/Q00/ouroboros/blob/40d04413e7e7eef324dc80504d1ce06e11ddd392/src/ouroboros/orchestrator/parallel_executor.py) (стр. 9708). **[код]** Именно здесь проверяется конкретный критерий, а трёхступенчатый конвейер отвечает за общую картину.
- **Перепроверка самоотчёта исполнителя.** Исполнитель пишет «тесты прошли». Оркестратор находит в журнале реальных вызовов Bash команду, которую исполнитель действительно запускал, и повторяет её в изолированной копии рабочей папки. Повторяются только команды из белого списка: тест-раннеры, сборка; сеть, удаление, git-запись и установка пакетов запрещены. См. [orchestrator/evidence/command_replay.py](https://github.com/Q00/ouroboros/blob/40d04413e7e7eef324dc80504d1ce06e11ddd392/src/ouroboros/orchestrator/evidence/command_replay.py). **[код, только шапка модуля и точки вызова]**

Заявлено в README: «3-stage gate: Mechanical ($0) → Semantic → Multi-Model Consensus». **[заявлено]** Из README не видно, что ступени 2–3 только совещательные. Это видно лишь в коде и в скилле [skills/evaluate/SKILL.md](https://github.com/Q00/ouroboros/blob/40d04413e7e7eef324dc80504d1ce06e11ddd392/skills/evaluate/SKILL.md).

**Полезно для наших слоёв.**
- *Проверка (после MVP):* брать правило «одобряют только выполненные команды, LLM может только задержать». Добавить три честных исхода: «принято», «отклонено», «не проверено». Сюда же — повтор команд из самоотчёта агента, а не доверие к тексту.
- *Последствия правок:* ступень 1 у Q00 гоняет все тесты проекта. У нас есть карта и последствия правок, поэтому можем запускать только затронутые тесты. Это наше преимущество, у Q00 его нет.
- *Знания проекта:* файл `.ouroboros/mechanical.toml` с подтверждёнными командами проекта — хороший пример «знания проекта», которое стоит хранить в git для всей команды.

**Можно ли взять код.** MIT, Python. Модули `pipeline.py` и `models.py` отделяются неплохо: у них чистые dataclass-типы и понятные функции. Но они тянут `LLMAdapter`, события и конфиг Q00. Если наш плагин будет не на Python, переносить нужно логику (≈100 строк правил), а не код.

**Слабые места.**
- Если в проекте нет ни линтера, ни тестов, одобрения не будет никогда: только `unverified`.
- Ступень 1 проверяет, что проект зелёный, а не что критерий выполнен.
- Команды для ступени 1 находит LLM. Проверка по диску защищает от выдуманных команд, но не от неподходящих.
- «Мультимодельный» консенсус на одном провайдере — это одна модель в трёх ролях.
- Сложность огромная: `parallel_executor.py` — 13 158 строк.

**Вердикт: взять идею.** Правило «одобряет только исполненное доказательство, LLM только блокирует», три исхода и перепроверку самоотчёта.

### Приём Q2. Скрытие проверочной команды и ожидаемого результата от исполнителя

**Что это и зачем.** У критерия приёмки может быть команда проверки (`verify_command`) и строка, которая должна быть в её выводе (`output_assertion`). Если исполнитель видит их, он может «подогнать» результат под проверку, например напечатать нужную строку. Поэтому исполнитель получает только цель и список ожидаемых файлов, а проверку запускает система.

**Как устроено на самом деле.**

- **Текст задачи для исполнителя.** `_build_success_contract_block` в [orchestrator/atomic_prompt_builder.py](https://github.com/Q00/ouroboros/blob/40d04413e7e7eef324dc80504d1ce06e11ddd392/src/ouroboros/orchestrator/atomic_prompt_builder.py) (стр. 34) пишет исполнителю только `expected_artifacts` и фразу «система независимо проверит контракт». Команда и ожидаемый вывод в текст не попадают. **[код]**
- **Спецификация, передаваемая в плагин.** В [mcp/tools/seed_handoff.py](https://github.com/Q00/ouroboros/blob/40d04413e7e7eef324dc80504d1ce06e11ddd392/src/ouroboros/mcp/tools/seed_handoff.py) заданы `_HIDDEN_WORKER_KEYS = {"verify_command", "output_assertion"}` (стр. 15). `project_worker_safe_seed` (стр. 83) делает так: **[код]**
  - вырезает эти ключи из YAML спецификации;
  - дополнительно ищет их значения во всех остальных полях и заменяет;
  - если YAML битый, исполнитель не получает его вовсе (fail closed).
- Полная спецификация хранится в процессе MCP-сервера в «сейфе» `SeedHandoffRegistry`. Исполнитель получает только непрозрачный id, а погасить этот id можно один раз и только для той же сессии. **[код]**
- **Подсказки при повторе.** Когда критерий провален и исполнителя запускают снова, в подсказку попадает вывод проверки. `_sanitize_fragment` в [orchestrator/retry_hints.py](https://github.com/Q00/ouroboros/blob/40d04413e7e7eef324dc80504d1ce06e11ddd392/src/ouroboros/orchestrator/retry_hints.py) (стр. 38) обрабатывает его так: **[код]**
  - заменяет точные значения;
  - полностью выбрасывает фрагмент, если в нём есть «преобразованный» вариант скрытого значения.
- **Как ищутся скрытые значения.** [orchestrator/contract_redaction.py](https://github.com/Q00/ouroboros/blob/40d04413e7e7eef324dc80504d1ce06e11ddd392/src/ouroboros/orchestrator/contract_redaction.py) проверяет исходный вид, `repr`, shell-кавычки, JSON-кавычки, HTML-сущности, `\x`/`\u`-экранирование, ANSI-коды и т.п. **[код]**
- **Журнал и история эволюции** хранят только описания критериев, «never verify_command/output_assertion» (комментарии в `events/lineage.py`, `evolution/loop_support.py`). **[код, только комментарии]**
- **Более строгий режим — «пакет проверок» (check package).** Это отдельный пакет [src/ouroboros/boundary/](https://github.com/Q00/ouroboros/tree/40d04413e7e7eef324dc80504d1ce06e11ddd392/src/ouroboros/boundary), ~15 тыс. строк. См. [boundary/run_wiring.py](https://github.com/Q00/ouroboros/blob/40d04413e7e7eef324dc80504d1ce06e11ddd392/src/ouroboros/boundary/run_wiring.py) и [boundary/oracle.py](https://github.com/Q00/ouroboros/blob/40d04413e7e7eef324dc80504d1ce06e11ddd392/src/ouroboros/boundary/oracle.py). **[код, по шапкам модулей и конфигу]** Как он работает:
  - До старта исполнителя отдельный вызов модели (только чтение) строит «оракулы»: входы и ожидаемые выходы по каждому критерию, в том числе **скрытые кейсы**, которых нет в спецификации.
  - Пакет хэшируется и «запечатывается», затем проверяется на исходном коде.
  - Журнал не даёт запустить исполнителя, пока пакет не запечатан и не принят.
  - После исполнителя пакет прогоняют на результате.
  - Скрытые входы и ожидания **никогда не пишутся на диск**, они живут только в памяти процесса. В квитанциях остаются только id кейса и pass/fail (`redact_held_out`).
  - Сравнение ожиданий идёт в процессе контроллера, а не в процессе проверяемого кода, поэтому подмена stdlib или monkeypatch не может «подделать» сравнение.
  - Если процесс перезапустился, скрытые кейсы потеряны, и критерии остаются нерешёнными.
  - По конфигу включено по умолчанию: `check_package: None` означает `on`, см. [config/models.py](https://github.com/Q00/ouroboros/blob/40d04413e7e7eef324dc80504d1ce06e11ddd392/src/ouroboros/config/models.py), стр. 816–830. При этом docstring `run_wiring.py` называет режим «opt-in». Это расхождение в самом проекте.
- **Что заявлено.** В описании плагина ([.claude-plugin/plugin.json](https://github.com/Q00/ouroboros/blob/40d04413e7e7eef324dc80504d1ce06e11ddd392/.claude-plugin/plugin.json)) авторы прямо признают: вырезание идёт «literally over five encodings, so a reshaped copy can still get through». То есть пересказанная копия может просочиться, и это тянется открытой задачей. **[заявлено]**

### Приём Q3. Журнал событий (EventStore)

**Что это и зачем.** Все изменения состояния (сессия началась, критерий принят, ступень проверки завершена и т.п.) записываются как неизменяемые события. Состояние можно восстановить повтором событий, например продолжить «ralph»-цикл после перезагрузки.

**Как устроено на самом деле.**

  - `id` (UUID);
  - `type` в формате `точка.через.точку.прошедшее_время`, например `execution.ac.completed`;
  - `timestamp`;
  - `aggregate_type` и `aggregate_id` («к чему относится»);
  - `data` (JSON);
  - `consensus_id`;
  - `event_version` для эволюции схемы.
  
  Перед записью из `data` вычищаются «сырые» полезные нагрузки: ключи `raw_*`, `subscribed_*`.
- **Таблица** — `events` в [persistence/schema.py](https://github.com/Q00/ouroboros/blob/40d04413e7e7eef324dc80504d1ce06e11ddd392/src/ouroboros/persistence/schema.py) (стр. 42): id, aggregate_type, aggregate_id, event_type, payload (JSON), timestamp, consensus_id. Рядом лежат маленькие таблицы-«замки» (`session_terminal_guards`, `session_start_guards`, `ac_acceptance_guards`). Они не дают двум процессам одновременно, например, завершить одну сессию. Сам поток событий остаётся только на добавление. **[код]**
- **Хранилище** — `EventStore` в [persistence/event_store.py](https://github.com/Q00/ouroboros/blob/40d04413e7e7eef324dc80504d1ce06e11ddd392/src/ouroboros/persistence/event_store.py) (стр. 498), 3100 строк. **[код]**

  - Методы: `append`, `append_batch`, `append_durable` (с дедлайном), условные записи (`append_session_start_if_absent`, `append_session_terminal_if_active`), `replay(aggregate_type, aggregate_id)` (стр. 1684, сортировка по времени и id), `get_events_after`, `query_*`, `replay_lineage`, `checkpoint_wal`.

**Полезно для наших слоёв.**
- *Журнал работы (личный):* прямая модель. Храним событие «что сделано» с типом, объектом (файл, символ, задача), временем и данными, только на добавление. Состояние («над чем я работал, что уже проверено») восстанавливается из событий. Поля `aggregate_type/aggregate_id` хорошо ложатся на наши объекты карты кода: файл, символ, модуль.

**Вердикт: взять идею.** Схема «событие = тип + объект + время + данные + версия», только добавление, восстановление повтором. Для личного журнала взять, для общих знаний в git — нет.

### Отдельно: оценка неясности (идея для `claude-tasks`)

Q00 перед генерацией спецификации считает «неясность» так: `Ambiguity = 1 − Σ(ясность_i × вес_i)`. Каждое измерение LLM оценивает от 0 до 1 при temperature 0.1. Измерения и веса:
- цель — 40%;
- ограничения — 30%;
- критерии успеха — 30%;
- для существующего кода (brownfield) добавляется «понятность контекста» — 15%, а веса становятся 35/25/25/15.

Если итог больше 0.2, генерация блокируется, пока пользователь явно не скажет `force`. Для автозавершения есть ещё пороги по каждому измерению: цель ≥ 0.75, ограничения ≥ 0.65, критерии ≥ 0.70. См. [bigbang/ambiguity.py](https://github.com/Q00/ouroboros/blob/40d04413e7e7eef324dc80504d1ce06e11ddd392/src/ouroboros/bigbang/ambiguity.py) (стр. 44–56) и README, раздел «Ambiguity Score». **[код]**

Для `claude-tasks` это дешёвая идея: при создании задачи оценивать по тем же трём–четырём осям, насколько понятны «Что», «Готово, когда» и «Критерии готовности». Если хоть одна ось ниже порога, задавать уточняющий вопрос. В наш плагин карты и памяти это не входит.

## razzant/ouroboros

### Приём R1. Ревью отдельным агентом

**Что это и зачем.** Изменение проверяет не тот, кто его написал. Автор «замораживает» итоговый дифф (коммит base..head) и отдаёт его отдельному агенту в чистом контексте. Тот читает репозиторий, ничего не правит и выдаёт структурированный вердикт.

**Как устроено на самом деле.** Есть два уровня: процесс для людей и внешних агентов (CONTRIBUTING) и встроенный конвейер самого агента.

**(а) Процесс для внешних вкладов** — [CONTRIBUTING.md](https://github.com/razzant/ouroboros/blob/1c8bb2170c2e1fc6c2ab75f7a23db16de9a35f6e/CONTRIBUTING.md), раздел 5 «Review the Frozen Diff in a Separate Agent Context». **[заявлено — это процесс, а не код]**
- Перед ревью изменение закоммичено, `git status --short` пуст. Ревьюируется диапазон `base SHA..head SHA`, а не незакоммиченные правки.
- Ревьюер — **отдельный контекст**: субагент, новая задача или новая сессия. Ревью в том же разговоре не засчитывается. Ревьюер **не правит** кандидата.
- Ревьюер получает цель, не-цели, точные SHA и доступ к репозиторию, читает CONTRIBUTING и чек-лист целиком, архитектурные документы — по нужным разделам.
- Ответ — **JSON-массив по 8 пунктам** чек-листа «Intent / Scope» ([docs/CHECKLISTS.md](https://github.com/razzant/ouroboros/blob/1c8bb2170c2e1fc6c2ab75f7a23db16de9a35f6e/docs/CHECKLISTS.md), стр. 946+): `intent_alignment`, `forgotten_touchpoints`, `cross_surface_consistency`, `regression_surface`, `prompt_doc_sync`, `architecture_fit`, `cross_module_bugs`, `implicit_contracts`.
  - Строки PASS обязательны и должны называть конкретный проверенный артефакт. Голое «PASS» считается провалом ревьюера.
  - Строка FAIL несёт серьёзность (critical/advisory), а critical называет точный файл или символ.
  - Итог: PASS / NEEDS_CHANGES / INCOMPLETE.
- Форма JSON проверяется скриптом [scripts/validate_scope_receipt.py](https://github.com/razzant/ouroboros/blob/1c8bb2170c2e1fc6c2ab75f7a23db16de9a35f6e/scripts/validate_scope_receipt.py). Авторы прямо пишут: «validates SHAPE, not truth».
- Любое изменение после ревью делает его устаревшим. Если отдельного контекста нет, ставится `NOT_RUN` с причиной, а не самопроверка.
- Мейнтейнерский скрипт [scripts/run_external_review.py](https://github.com/razzant/ouroboros/blob/1c8bb2170c2e1fc6c2ab75f7a23db16de9a35f6e/scripts/run_external_review.py) `--contributor` делает то же автоматически. **[код, шапка]** Важная деталь: ревью всегда выполняется **механизмом ревью из базового коммита**, скрипт перезапускает себя из detached-worktree базы. Так предложение не может ослабить собственного проверяющего. Коды выхода: 0 — прошло, 1 — настоящий блок, 3 — «это не вердикт» (сбой транспорта, потеря кворума и т.п.).

**(б) Встроенный конвейер `commit_reviewed`** — агент сам коммитит свои правки только через него. **[код, по шапкам модулей и точке входа]** Стадии:
1. **Подготовка.** Проверки прав и незавершённой работы, индексация, защищённые пути, «отпечаток» staged-диффа: [tools/git_review_cycle.py](https://github.com/razzant/ouroboros/blob/1c8bb2170c2e1fc6c2ab75f7a23db16de9a35f6e/ouroboros/tools/git_review_cycle.py), `_run_reviewed_stage_cycle` (стр. 603).
2. **Предварительное (advisory) ревью.** Дешёвое ревью только для чтения, можно пропустить с записью в аудит: [tools/claude_advisory_review.py](https://github.com/razzant/ouroboros/blob/1c8bb2170c2e1fc6c2ab75f7a23db16de9a35f6e/ouroboros/tools/claude_advisory_review.py).
3. **Параллельно две ветки**, [tools/parallel_review.py](https://github.com/razzant/ouroboros/blob/1c8bb2170c2e1fc6c2ab75f7a23db16de9a35f6e/ouroboros/tools/parallel_review.py), `run_parallel_review` (стр. 538):
   - **Triad** — три модели смотрят staged-дифф по чек-листу «Repo Commit Checklist» и отвечают JSON-массивом. Общий разбор ответов и подсчёт кворума: [triad_review.py](https://github.com/razzant/ouroboros/blob/1c8bb2170c2e1fc6c2ab75f7a23db16de9a35f6e/ouroboros/triad_review.py).
   - **Scope** — ревьюер, который **сам читает репозиторий** инструментами только для чтения: `read_file`, `list_files`, `search_code`, `query_code`, `vcs_diff`, сеть выключена. Он получает цель, полный дифф, список затронутых путей, компактный индекс репозитория и **«манифест обязательных источников»** — связанные с изменением файлы, которые он должен прочитать. Код: [tools/scope_review.py](https://github.com/razzant/ouroboros/blob/1c8bb2170c2e1fc6c2ab75f7a23db16de9a35f6e/ouroboros/tools/scope_review.py) (`run_scope_review`, стр. 392), [tools/scope_review_session.py](https://github.com/razzant/ouroboros/blob/1c8bb2170c2e1fc6c2ab75f7a23db16de9a35f6e/ouroboros/tools/scope_review_session.py), [tools/scope_required_sources.py](https://github.com/razzant/ouroboros/blob/1c8bb2170c2e1fc6c2ab75f7a23db16de9a35f6e/ouroboros/tools/scope_required_sources.py). Полнота прочтения записывается как диагностика («прочитал ли то, что должен»), но на вердикт не влияет.
4. **Тесты** — «герметичный» прогон всей батареи во временном worktree ([ouroboros/tools/git.py](https://github.com/razzant/ouroboros/blob/1c8bb2170c2e1fc6c2ab75f7a23db16de9a35f6e/ouroboros/tools/git.py), `run_tests_preflight_with_proof`).
5. **Привязка к публикации.** Созданный коммит сверяется с тем, что ревьюировали. Любое изменение, rebase или разрешение конфликта требует нового ревью.

Правила вокруг конвейера — [docs/development/05-review-and-commit-protocol.md](https://github.com/razzant/ouroboros/blob/1c8bb2170c2e1fc6c2ab75f7a23db16de9a35f6e/docs/development/05-review-and-commit-protocol.md) и [tools/commit_gate.py](https://github.com/razzant/ouroboros/blob/1c8bb2170c2e1fc6c2ab75f7a23db16de9a35f6e/ouroboros/tools/commit_gate.py). **[заявлено + частично код]**
- Платных циклов ревью по умолчанию не больше 2 (`OUROBOROS_REVIEW_MAX_CYCLES`).
- **Байт-в-байт тот же дифф повторно не ревьюируется**, а бесплатно отклоняется с цитатой прошлого вердикта.
- Возражение автора (rebuttal) идентифицируется по sha256 содержимого: новое покупает ровно одно повторное ревью, повтор бесплатно отклоняется.
- «Технический сбой ревью» и «разрешение на коммит» — разные факты: сбой никогда не превращается в PASS.

Помимо коммитов есть «приёмка задачи» (task acceptance) — такая же панель ревьюеров над результатом задачи: [loop_acceptance_review.py](https://github.com/razzant/ouroboros/blob/1c8bb2170c2e1fc6c2ab75f7a23db16de9a35f6e/ouroboros/loop_acceptance_review.py). **[код, шапка]**

**Полезно для наших слоёв.**
- *Проверка (после MVP):* почти готовый рецепт для Claude Code. Отдельный субагент без права записи; вход — замороженный диапазон `base..head`; выход — JSON-чек-лист с обязательным обоснованием PASS; `NOT_RUN` вместо молчания; повторный дифф не ревьюируем.

Это материал для F01-01.

**Можно ли взять код.** MIT, Python, но код связан с биллингом, «custody» процессов и маршрутизацией моделей. Отделить нельзя. Брать стоит текст: 8 пунктов чек-листа с формулировками (переписать своими словами), инструкцию ревьюеру из CONTRIBUTING и форму JSON-ответа.

  - Заводится `data/state/headless_tasks/<task_id>/data` с папками `memory`, `logs`, `state`, `task_results`.
  - `_copy_stable_memory` (стр. 927) копирует `identity.md`, `WORLD.md`, `registry.md` и всю папку `knowledge/`.
  - **Если задача привязана к проекту, копируется только `knowledge/patterns.md`**, без глобальных знаний.
  - Диалог, черновик, почта и история не копируются.
- **Возврат** — при завершении `build_memory_export` (стр. 902) собирает все текстовые файлы памяти копии в `memory_export.json` и кладёт как артефакт задачи. **Слияния в родительскую память нет** — это прямо сказано в docstring («without merging it into parent memory»). **[код]**
- **Факты проекта** живут отдельно от копии: `DATA_DIR/projects/<id>/knowledge`. Поэтому они переживают forked-запуски и не попадают в копию для чужого проекта. См. [ouroboros/project_facts.py](https://github.com/razzant/ouroboros/blob/1c8bb2170c2e1fc6c2ab75f7a23db16de9a35f6e/ouroboros/project_facts.py). **[код, шапка]**
- **Чего forked не изолирует** — по архитектуре ([docs/architecture/01-high-level-architecture.md](https://github.com/razzant/ouroboros/blob/1c8bb2170c2e1fc6c2ab75f7a23db16de9a35f6e/docs/architecture/01-high-level-architecture.md), раздел CLI / Headless Boundary): «identity and scratchpad writes still land on the canonical root». То есть запись в identity и черновик из задачи всё равно попадает в общую память. **[заявлено]**
- Копии удаляются по сроку хранения через `task_custody.settle_child_drive`. **[код, по вызову]**

**Полезно для наших слоёв.**
- *Журнал работы и знания проекта:* это готовая схема разделения «личное / общее»:
  1. Задача пишет выводы в свой черновик (копию).
  2. На выходе получается явный «экспорт».
  3. В общие знания команды экспорт попадает только **явным действием**: у нас это коммит/PR в git с ревью, у razzant — ручное решение.
- Правило «проектная задача получает только проектные паттерны, но не глобальные знания» переносится как «знания проекта A не просачиваются в проект B».
- Для работы субагентов Claude Code: субагенту давать снимок знаний (read-only), а его находки забирать отдельным артефактом.

**Можно ли взять код.** MIT, Python. Сами функции `prepare_task_drive`/`_copy_stable_memory`/`build_memory_export` — около 80 строк, простые, их легко переписать на любом языке. Остальное (сроки, custody, копирование результатов назад) завязано на их супервизор.

**Слабые места.**
- Изоляция неполная: identity и черновик пишутся в общий корень.
- Экспорт — просто свалка всех файлов памяти без диффа относительно исходной копии. Понять, что задача узнала нового, нужно самому.
- Автоматического пути «предложить в общие знания» нет вовсе.

**Вердикт: взять идею.** Для нас она ключевая: копия на задачу → явный экспорт → слияние только через git. Код тривиален, переписать.

### Приём R3. Результат задачи патчем

**Что это и зачем.** Результат задачи над внешним проектом — не «ответ модели», а проверяемый артефакт: git-патч относительно базового коммита плюс манифест. По нему скрипты и люди понимают, что именно изменилось, что исключено и почему.

**Как устроено на самом деле.**

- **CLI.** `ouroboros run --workspace <папка> --patch` печатает патч вместо ответа, `--patch-out <файл>` сохраняет его. Режим строгий: провал, отсутствие изменений, пустой или незавершённый патч — это ошибка с ненулевым кодом (`_patch_from_result`, стр. 902). См. [ouroboros/cli.py](https://github.com/razzant/ouroboros/blob/1c8bb2170c2e1fc6c2ab75f7a23db16de9a35f6e/ouroboros/cli.py), стр. 529–530 и 902. **[код]**
- **Сборка патча** — `write_workspace_patch_artifacts` в [ouroboros/workspace_patch_capture.py](https://github.com/razzant/ouroboros/blob/1c8bb2170c2e1fc6c2ab75f7a23db16de9a35f6e/ouroboros/workspace_patch_capture.py) (стр. 71). **[код]**
  - База — зафиксированный при старте задачи HEAD (`base_sha`), а не текущий `HEAD`. Поэтому коммиты, сделанные агентом внутри задачи, тоже попадают в патч. Для пустого репозитория база — пустое дерево.
  - Берутся изменённые отслеживаемые файлы (`git diff base`) и неотслеживаемые (`git ls-files --others --exclude-standard`, то есть с учётом `.gitignore`).
  - Пофайловые исключения с причиной:
    - «одноразовые проверочные файлы», которые агент объявил через `scratch=[...]`: исключаются, только пока их sha не изменился;
    - файлы, похожие на секреты: `.netrc`, `credentials.json`, `id_rsa`, приватные PEM-ключи, в манифесте они идут как `sensitive_blocked`;
    - мусор: `__pycache__`, `node_modules`, `.pytest_cache`, `*.pyc`, `coverage.xml` и т.п.;
    - lock-файл без изменения соседнего манифеста (например, `package-lock.json` без `package.json`);
    - неотслеживаемые файлы больше 5 МиБ и бинарные — уходят в отдельные файлы-артефакты (zip+манифест), а не в патч.
  - Правила собраны в отдельном «чистом» модуле без git и файловой системы: [ouroboros/workspace_patch_rules.py](https://github.com/razzant/ouroboros/blob/1c8bb2170c2e1fc6c2ab75f7a23db16de9a35f6e/ouroboros/workspace_patch_rules.py), 178 строк.
- **Манифест** `workspace_patch.json` пишется **всегда**, даже если изменений нет или всё упало, а сам `workspace.patch` — только при статусе `ready_with_changes`. Манифест — источник правды: он отличает «не делали», «нет изменений» и «сломалось». **[код + заявлено в архитектуре]**
- Финализация задачи ([ouroboros/headless.py](https://github.com/razzant/ouroboros/blob/1c8bb2170c2e1fc6c2ab75f7a23db16de9a35f6e/ouroboros/headless.py), `_finalize_task_artifacts_locked`, стр. ~752) складывает патч, манифест и `memory_export.json` в артефакты задачи. **[код]**
- **Важно: патч — это запись, а не песочница.** Агент правит рабочую папку проекта напрямую. В архитектуре прямо сказано, что исполнитель рабочей папки — «a process-routing boundary, not a sandbox». **[заявлено]**

**Полезно для наших слоёв.**
- *Проверка перед слиянием:* проверяем «патч + манифест», а не рабочую папку. База — зафиксированный SHA начала работы, и тогда промежуточные коммиты агента не теряются.
- Правила исключений (секреты, мусор, lock-файлы без манифеста) пригодятся как фильтр перед ревью и перед записью в общие знания: чтобы секрет не попал в git через «знания».
- *Журнал работы:* событие «задача завершена» ссылается на патч и манифест (sha256, размер). Это даёт проверяемую связь «запись в журнале → реальное изменение кода».
- *Последствия правок:* список путей из патча — прямой вход для расчёта последствий правок.

**Можно ли взять код.** MIT. `workspace_patch_rules.py` маленький и чистый, его списки и регулярки можно перенести с указанием источника. `workspace_patch_capture.py` (897 строк) завязан на их контракт задачи и артефакты, лучше написать своё по той же схеме.

**Слабые места.**
- Изоляции нет: если нужна настоящая песочница, её надо делать отдельно (git worktree).
- Секреты ловятся по имени файла, а не по содержимому (кроме PEM).
- Логика базы довольно запутанная: разные правила для «своего worktree» и общего дерева.

**Вердикт: взять идею** (патч от зафиксированной базы + манифест исключений, который пишется всегда). **Код — только правила исключений** из `workspace_patch_rules.py`, с указанием источника.

1. **Проверка перед слиянием (после MVP)** складывается из Q1 + Q2 + R1 + R3:
   - вход — патч от зафиксированной базы с манифестом (R3);
   - механическая часть — только затронутые тесты и линтеры по нашей карте последствий, решает код выхода (Q1);
   - смысловая часть — отдельный read-only субагент с чек-листом, который получает от нашей карты список обязательных к прочтению файлов (R1);
   - LLM может только задержать слияние (Q1);
   - если ничего не выполнилось, итог — «не проверено» (Q1/R1 `NOT_RUN`);
   - проверки запускает система, а не агент (Q2).
2. **Журнал работы** — события только на добавление по схеме Q3. Черновик ограничен по размеру, вытесненное уходит в журнал (R4). События «задача завершена» ссылаются на патч (R3).
3. **Знания проекта в git** — markdown-темы с генерируемым оглавлением (R4). Из задачи они попадают туда только через явный экспорт и коммит (R2). Автоматическая запись ограничена белым списком и срабатывает только по типизированным событиям (R4). Перед записью действует фильтр секретов (R3).
4. **Чего ни у кого из двоих нет и что мы делаем сами:** общие знания команды с merge через git и карта кода как вход для проверки. У обоих проектов всё рассчитано на одного пользователя на одной машине.
