## 1. Graft

### Что это и для чего

Локальный «слой контекста» для coding-агента. Строит граф символов репозитория через tree-sitter и отдаёт его агенту через CLI, MCP и хуки Claude Code. Опционально (`--deep`) пишет через LLM описания узлов в Markdown. Кроме того, в репозитории есть облачная часть Trail («brain»: правила для CLAUDE.md/AGENTS.md из истории коммитов и обсуждений PR) и GitHub App для отчётов по PR.

### Как устроено на самом деле

**Разбор кода [код].** Два уровня:
- «Глубокий» уровень — вручную написанные извлекатели на нативном tree-sitter: TS/JS (включая JSX/TSX), Python, Go, Java, Kotlin, Swift, PHP, R. Таблица расширений — `src/graph/extract.ts` (`EXTENSIONS`). Для вызовов методов есть вывод типа получателя (`obj.method()` → тип `obj`) по присваиваниям в конструкторе и аннотациям типов: `src/graph/bindings.ts`.
- «Широкий» уровень — один общий извлекатель на WASM-грамматиках и файлах запросов `tags.scm`: `src/graph/generic.ts` + `src/graph/queries/*.scm`. Сюда попадают **Rust, C#**, C, C++, Ruby, Scala, Elixir, Solidity, OCaml, Zig, Dart, Clojure, Nix, Lua. Выдаёт только символы и вызовы по голому имени, без типа получателя. Новый язык = одна строка в `GENERIC_LANGS` + один `.scm`-файл.
- Файлы-контейнеры (`.vue`) — `src/graph/container.ts`: вырезает блок `<script>` и отдаёт его глубокому извлекателю со сдвигом номеров строк.
- Необязательный режим `graft build --lsp` — `src/graph/lsp/enrich.ts`, `src/graph/lsp/registry.ts`: для каждой функции спрашивает у языкового сервера исходящие вызовы (call hierarchy) и добавляет рёбра с меткой `lsp_resolved`. Серверы: rust-analyzer, clangd, gopls, pyright, typescript-language-server. **Для C# сервера нет.** `pickServer()` выбирает **один** сервер на весь репозиторий (первый подходящий по приоритету), поэтому в смешанном репозитории Rust + TS обогатится только Rust. Поиск бинарника делается через `command -v` (`execSync`) — на Windows без POSIX-оболочки это, судя по коду, не сработает.

**Модель графа [код]** — `src/graph/types.ts`:
- Узел: `file | class | function | method | interface | type | enum | struct | trait | module | constant | variable`; поля `id` (вида `src/cache.ts#Cache.get`), `path`, `span` (`L165-L222`), `signature`, `exported`, `origin` (`ast` / `generic`), `body_hash`, для `--deep` — `summary` и `crux` (ключевые строки кода, хранятся текстом, а не номерами строк).
- Ребро: `contains | calls | imports | references | implements | extends` и **уверенность** `lsp_resolved | lsp_dispatch | extracted | inferred`.
- Правило разрешения (`src/graph/resolve.ts`): совпадение в том же файле → `extracted`; единственное совпадение имени по всему репозиторию → `inferred`; **несколько кандидатов → ребро отбрасывается, а не угадывается**. Вызов метода без известного типа получателя тоже отбрасывается (в комментарии: подбор по имени «вдвое снижал точность рёбер вызова, 73% → 37%»). Есть защита от связей между языками, которые не могут вызывать друг друга (`FAMILIES`: TS/JS, JVM, C/C++).
- Вторая, «смысловая» модель — Markdown-узлы в `graft/*.md` (подсистемы и понятия, связи `depends_on / part_of / uses / implements / produces` в виде `[[wikilinks]]`), строится LLM: `src/context/build.ts`, `src/context/node-file.ts`. Ниже сгенерированного блока можно писать свои заметки, они сохраняются при пересборке [README; сохранение блока — `node-file.ts`].

**Хранение [код].** Всё — файлы: `graft/.graph/wiring.json` (граф символов), карточки по файлам, `graft/*.md`, кэши в `graft/.cache/` (`extract.json`, `ask-index.json`, `summaries.json`). Папка `graft/` автоматически добавляется в `.gitignore` — это локальный кэш, а не общее знание команды. Никакой БД и эмбеддингов; поиск — BM25 по имени, сигнатуре и телу (`src/ask/ask.ts`).

**Инкрементальное обновление [код].**
- `src/graph/fingerprint.ts` — быстрая проверка рабочего дерева (размер + mtime, по желанию хеш).
- `src/graph/extract-cache.ts` — результат разбора каждого файла кэшируется по содержимому; кэш сбрасывается и при изменении самого кода извлекателя (хеш исходника извлекателя). Разрешение связей при этом **каждый раз пересчитывается по всему графу** (дёшево, но это полный проход).
- `src/graph/refresh.ts` — **перед каждым запросом** граф сверяется с рабочим деревом и при расхождении перестраивается (только структурная часть, без LLM). Незакоммиченные правки учитываются. Защита от параллельных пересборок — файл-замок.
- LLM-часть (`--deep`) автоматически не обновляется никогда.

**Инструменты MCP [код]** — `src/mcp/tools.ts`, `src/mcp/tool-names.ts`: 6 инструментов — `graft_find_code`, `graft_file_api`, `graft_trace_calls` (кто вызывает / что вызывает, глубина N или `all`), `graft_find_all` (regex с группировкой по символу), `graft_repo_map`, `graft_check_freshness`. Описания короткие: около 2,5 тыс. символов на все шесть (≈ 700 токенов). Плюс строка `instructions` в ответе `initialize` (`src/mcp/instructions.ts`, лимит ~1000 символов) — она доходит до агента даже тогда, когда Claude Code откладывает схемы инструментов, и прямо учит загружать все шесть одним `ToolSearch`.

**Хуки Claude Code [код]** — `src/claude/settings-merge.ts`, `src/claude/hooks.ts`:
- `SessionStart` — карта репозитория в начале сессии;
- `UserPromptSubmit` (15 с) — `graft ask` по тексту запроса, подходящие узлы подмешиваются в контекст;
- `PostToolUse` на `Write|Edit|MultiEdit` — «радиус поражения» правки (кто зависит от файла) и отметка «граф устарел»;
- `PostToolUse` на `Bash|mcp__graft__|Read|Grep|Glob` — учёт экономии токенов (статистика);
- `Stop` — фоновая пересборка после хода.
Также statusline и skill-файл `.claude/skills/graft/SKILL.md` (~9 КБ). Настройки сливаются, чужие не затираются; есть `graft uninstall`.

**Последствия правок [код].** `graft callers <symbol> -d N` и `graft blast` (`src/blast/*.ts`): берёт изменённые строки из `git diff`, находит самый внутренний символ, обходит входящие рёбра. Для каждой затронутой области даёт сигнал по тестам: `changed` / `stale` / `none` — есть ли тесты, которые достают до области, и тронуты ли они в этом diff (`src/blast/blast.ts`). Тест определяется по пути (`isTestPath` в `src/ask/ask.ts`: `test/`, `__tests__`, `.test.`, `.spec.`, `_test.go`). «Кого позвать на ревью» — по `git blame` (`src/blast/owners.ts`).

### Как работает с нашими языками

| Язык | Уровень | Импорты | Вызовы |
|---|---|---|---|
| **JS/TS** | глубокий | только относительные пути (`resolveImport` в `resolve.ts`: `if (!spec.startsWith(".")) return spec`). Алиасы `tsconfig` `paths` и пакеты workspace **не разрешаются** | свободные функции — хорошо; методы — если тип получателя выводится из конструктора/аннотации; иначе ребро отбрасывается. С `--lsp` — точно (при установленном `typescript-language-server`) |
| **Go** | глубокий | по `go.mod` (`resolveGoImport`) | функции пакета и методы через тип получателя (`bindings.ts`); `--lsp` с `gopls` |
| **Rust** | широкий | `use` разрешается (`resolveRustUse`) | по голому имени; метод вида `self.x()`/`a.b()` превращается в имя `b` и связывается, только если имя единственное в Rust-файлах; иначе отброшено. С `--lsp` + rust-analyzer — точно |
| **C#** | широкий | `using` **не извлекается** (в `queries/c_sharp.scm` нет захвата импортов) | только по голому имени, без типа получателя; LSP нет. Самое слабое место для Unity |
| Unity-ассеты | — | `.unity`, `.prefab`, `.meta`, `.asmdef` не читаются | методы, которые вызывает движок (`Update`, `Start`) и ссылки из сцен не видны |

### Что полезно для наших слоёв

- **Карта:** двухуровневая схема извлекателей (глубокий ручной + широкий на `tags.scm`) — готовый образец расширяемости модулями языков. Правило «лучше не ставить ребро, чем угадать» + метки уверенности + отдельная метка `lsp_resolved`. Уровни выдачи: `repo_map` → `file_api` (только сигнатуры) → `find_code` (фрагмент ≤ 8 строк) → полный текст (`full: true`).
- **Последствия правок:** `blast` по diff с посимвольной привязкой и сигналом «тесты не тронуты».
- **Свежесть:** проверка отпечатка рабочего дерева перед каждым запросом — дешёвый и надёжный приём.
- **Интеграция с Claude Code:** набор из пяти хуков и `instructions` в MCP — прямой образец для нашего плагина.
- **Документы:** своих Markdown-документов проекта не индексирует; пишет свои.
- **Журнал / знания:** нет (Trail brain — облачный сервис, не локальная память).

### Можно ли взять код

MIT, TypeScript — лицензионно свободно. Отделяются хорошо: `src/graph/generic.ts` + `queries/*.scm` (почти самостоятельный модуль), `src/graph/resolve.ts`, `src/graph/refresh.ts` + `fingerprint.ts` + `extract-cache.ts`, `src/blast/*`, `src/claude/settings-merge.ts`. Глубокие извлекатели (`extract.ts`, 2561 строка, `bindings.ts`) сильно связаны между собой. Если наш плагин будет на TS/Node — код можно брать кусками; если на другом языке — брать идеи.

### Слабые места

- C# и Rust — на «широком» уровне: для Unity и наших Rust-расширений точность вызовов низкая.
- TS без `tsconfig paths` и workspace — в браузерных играх с алиасами импорты потеряются.
- LSP: один сервер на репозиторий, нет C#, поиск бинарника через `command -v`.
- Нет Markdown/PDF проекта в графе, нет памяти.
- Граф — локальный кэш вне git: команда не делит ни граф, ни заметки.
- Телеметрия включена по умолчанию (отключается `graft telemetry disable` / `DO_NOT_TRACK=1`, `TELEMETRY.md`). Облачная часть Trail отправляет наружу сообщения коммитов, комментарии PR, документы и id символов (`src/brain/push.ts`, `src/brain/upload.ts`).
- Бенчмарки в README — собственные, на своих задачах (заявлено, не проверялось).

### Вердикт: **взять идею, отдельные модули — взять код** (если выберем TS)

Берём: схему «глубокий + широкий уровень на `tags.scm`» как модель модулей языков; правило разрешения с отказом от угадывания и метками уверенности; проверку свежести перед запросом; `blast` по diff с сигналом по тестам; набор хуков Claude Code и `instructions` в MCP; компактный набор из ~6 инструментов.

## 2. CodeGraph

> **Какой CodeGraph.** Здесь разбирается только `codegraph-ai/CodeGraph` (Rust, модуль `codegraph-memory`). Это другой проект, не `colbymchenry/codegraph` (MIT), который разобран в `04-market.md`, §2.1. Сводка пользователя их не смешивает: всё, что она пишет о CodeGraph (Rust, 38 языков, 42 инструмента, `codegraph-memory`, `--graph-only`, профили, Pro), относится к `codegraph-ai/CodeGraph`.

### Что это и для чего

Один нативный бинарник на Rust (`codegraph-server`), который работает и как MCP-сервер, и как LSP-сервер для VS Code / JetBrains. Строит граф кода по 38 языкам, добавляет гибридный поиск (BM25 + эмбеддинги), память проекта, индекс Markdown-документов и отчёт по PR.

### Как устроено на самом деле

**Разбор кода [код].** По отдельному крейту на язык (`crates/codegraph-<lang>/src/{visitor,extractor,mapper,parser_impl}.rs`), общий контракт — трейт в `crates/codegraph-parser-api/src/traits.rs`. 38 крейтов перечислены в корневом `Cargo.toml`; README уточняет, что COBOL, Fortran, Perl, Dart, Zig, R собираются только с `--features extra-languages` [README]. Есть определение HTTP-обработчиков и тестов по атрибутам (для C# — `[Test]`, `[Fact]`, `[UnityTest]` через `has_test_attribute`, `crates/codegraph-csharp/src/visitor.rs`).

**Модель графа [код]** — `crates/codegraph/src/graph/types.rs`:
- Узлы: `CodeFile | Function | Class | Module | Variable | Type | Interface | Generic` + словарь свойств.
- Рёбра: `Imports | ImportsFrom | Contains | Calls | Invokes | Instantiates | Extends | Implements | Uses | Defines | References | RuntimeCalls`.
- `NodeId` — **монотонный счётчик u64**, при переиндексации файла узлы удаляются и создаются с новыми id.
- **Меток уверенности у рёбер нет** — есть только свойство `resolved_by: cross_file_resolution`.
- Межфайловое разрешение (`crates/codegraph-server/src/watcher.rs`, `resolve_cross_file_imports`): строится **одна глобальная карта «имя → узел»**. Если одинаковое имя встречается несколько раз, выбирается узел с большей «весом» (`complexity * 100 + lines`, функция `symbol_weight`). Вызовы, не найденные в файле, сохраняются в свойство `unresolved_calls` и затем связываются по этой карте. Проверки языка нет.

**Хранение [код].** Граф — RocksDB в `~/.codegraph/graph.db`, общий для всех проектов, с пространствами имён по slug проекта; при старте грузится в память (`crates/codegraph-server/src/mcp/server.rs`, `open_persistent_graph`). Память — отдельная RocksDB в `~/.codegraph/projects/<slug>/memory` (`crates/codegraph-server/src/memory.rs`). Документы — отдельное хранилище рядом (`docs`). То есть **всё хранится в домашней папке пользователя, вне репозитория и вне git**.

**Инкрементальное обновление [код].** Хеш содержимого FNV-1a (`crates/codegraph-server/src/indexer.rs`, `hash_content`); в MCP-режиме — наблюдатель за файлами с задержкой 2 с (`crates/codegraph-server/src/mcp/file_watcher.rs`): удаляет старые узлы файла, разбирает заново, переиндексирует зависимые, снова запускает межфайловое разрешение и пересобирает поисковые индексы. Инструменты `reindex_workspace`, `index_files`, `index_directory`.

**Инструменты MCP [код]** — `crates/codegraph-server/src/mcp/tools.rs`: 42 инструмента сообщества. Строки описаний и схем — около **26 тыс. символов (≈ 6–7 тыс. токенов)** на полный набор; описания длинные, в стиле «USE WHEN… PREFER THIS…». Профили `--profile` / `CODEGRAPH_TOOL_PROFILE` (`ToolProfile` в том же файле): `core` — 8, `graph` — 17, `memory` — 14, `all` — все. Инструменты переиндексации есть только в `all`. Pro-инструменты (безопасность, похожий код, история git) в репозитории отсутствуют — подключаются через `with_pro_provider`.

Ключевой инструмент `get_edit_context` (`crates/codegraph-server/src/domain/edit_context.rs`): исходник символа + вызывающие + связанные тесты + заметки памяти + последние коммиты по файлу, с бюджетом токенов и приоритетом «символ > вызывающие > тесты > заметки > история».
`find_related_tests` (`domain/related_tests.rs`): тесты, которые вызывают символ (обход до глубины 3), + тесты в том же и соседних файлах. Тест определяется по имени (`test_`, `Test…`, `_test`), атрибуту `is_test` или пути (`/test/`, `/tests/`, `.test.`, `.spec.`, `_test.`) — `ai_query/engine.rs`, `detect_entry_type`. Путь проверяется с учётом регистра: юнитиевская папка `Assets/Tests/` по пути не распознается, но C#-тесты всё равно ловятся по атрибуту.
`pr_context` — отчёт по PR: затронутые функции, вызывающие, покрытие тестами, устаревшие документы, рецензенты по `git blame`.

**Хуки [код].** В `mcp-package/hooks/codegraph-pre-edit.sh` и `.ps1` — один хук `PreToolUse` на правки: напоминает вызвать `codegraph_get_edit_context` / `analyze_impact`. Важно: хук возвращает `"permissionDecision": "allow"`, то есть **автоматически разрешает правку в обход запроса разрешения Claude Code**. Для нашего плагина так делать нельзя.

**Память (`codegraph-memory`) [код]** — `crates/codegraph-memory/src/{node,temporal,storage,search}.rs`:
- Виды записей: `ArchitecturalDecision`, `DebugContext`, `KnownIssue`, `Convention`, `ProjectContext`; источник (`UserProvided`, `ConversationDerived`, `GitHistory` …), теги, `confidence`, `agent_source`.
- Двойное время: `valid_at` / `invalid_at` (когда знание было верным) и `created_at` / `superseded_at` (когда записано), плюс `commit_hash`.
- Привязка к коду `code_links` — **по числовому id узла графа**.
- Поиск: BM25 + эмбеддинги (fastembed BGE-small или статические model2vec) + близость по графу, индекс HNSW.
- Автоматическая пометка «устарело» (`invalidate_for_code_nodes`) вызывается из LSP-бэкенда при удалении файла из графа и из наблюдателя за веткой (`backend.rs`, `branch_watcher.rs`). **В MCP-режиме наблюдатель за файлами память не трогает** (в `mcp/file_watcher.rs` вызовов нет). А поскольку id узлов меняются при каждой переиндексации файла, привязки заметок к коду, по коду, со временем указывают на несуществующие узлы. Это вывод из чтения кода, не проверено запуском.

**Документы [код]** — `crates/codegraph-memory/src/docs.rs`: Markdown режется по дереву заголовков, листья получают эмбеддинги; поиск по смыслу. `verify_design` / `design_gaps` — берут идентификаторы в обратных кавычках из документа и проверяют, есть ли такие имена в графе (`extract_identifiers`). Это проверка «имя существует», а не «поведение соответствует». Индексация — только явным вызовом `index_markdown` на каждый файл; документы — отдельное хранилище, **не узлы графа кода**. PDF не поддерживается.

### Как работает с нашими языками

| Язык | Импорты | Вызовы |
|---|---|---|
| **C#** | `using` → рёбра `Imports` | имя вызова берётся целиком как текст (`obj.Method`), срезаются только `this.`/`base.` (`extract_callee_name`). Межфайловая карта ключуется голыми именами, поэтому вызовы через объект **в основном остаются неразрешёнными**. Есть поддержка ASP.NET и `.aspx` |
| **JS/TS** | есть (`crates/codegraph-typescript`) | от вызова `obj.method()` остаётся голое `method` → глобальная карта имён → при совпадениях выбирается «самый сложный» символ. **Лишние (ложные) рёбра вероятны** |
| **Go** | есть | так же: `pkg.Fn` и `obj.M` → голое имя |
| **Rust** | есть | так же: `self.m()`, `a::b::c()` → последний сегмент |
| Unity-ассеты | нет | нет |

Итог: у C# рёбер вызовов мало, у TS/Go/Rust — много, но часть ложная, и отличить их нельзя, потому что меток уверенности нет.

### Что полезно для наших слоёв

- **Последствия правок:** состав `get_edit_context` (символ + вызывающие + тесты + заметки + история с бюджетом токенов) — ровно то, что нужно агенту перед правкой. Поиск связанных тестов (через граф + по соседним файлам + по атрибутам). Отчёт по PR с «тестовыми пробелами» и «устаревшими документами».
- **Журнал / знания:** схема записи памяти — виды записей, двойное время, привязка к коду, источник, `agent_source`. Хорошая основа для формата наших заметок.
- **Документы:** «проверка документации против кода» по идентификаторам в обратных кавычках — дешёвый полезный сигнал для будущей проверки.
- **Контекст:** профили инструментов как способ резать расход контекста.
- **Карта:** крейт на язык с общим трейтом — модульно, но тяжелее, чем `tags.scm`.

### Можно ли взять код

Apache-2.0 — можно, с сохранением NOTICE. Rust; ядро графа (`crates/codegraph`) и API парсеров отделяемы; сервер (`codegraph-server`, 41 тыс. строк, файлы по 4–5 тыс. строк) сильно связан. Тянет RocksDB, ONNX Runtime, fastembed — тяжело для плагина. Требует glibc ≥ 2.30 и libstdc++ из GCC 11 на Linux [README].

### Слабые места

- Межфайловые вызовы разрешаются угадыванием по имени без меток уверенности.
- Память и граф живут в `~/.codegraph`, не в git — командного знания нет.
- Привязка заметок к числовым id узлов, которые меняются при переиндексации.
- 42 инструмента ≈ 6–7 тыс. токенов описаний; профили помогают, но по умолчанию `all`.
- Хук `PreToolUse` с `permissionDecision: "allow"` обходит разрешения.
- Телеметрия PostHog включена по умолчанию (`mcp-package/bin/codegraph-daemon.js`, отключение `CODEGRAPH_TELEMETRY=off`).
- Один разработчик (по README), часть возможностей — в закрытой Pro-версии.

### Вердикт: **взять идеи, код не брать**

Берём: состав `get_edit_context`; алгоритм поиска связанных тестов; схему записи памяти (виды, двойное время, источник, привязка к коду); профили инструментов; проверку «документ ↔ код» по идентификаторам; отчёт по PR. Не берём: разрешение по глобальной карте имён, хранение в домашней папке, id-привязки, автоматическое `allow` в хуке.

## 3. Graphify

### Что это и для чего

Skill для coding-агентов плюс Python-библиотека. Превращает папку с кодом, документами, PDF, картинками и видео в граф знаний (`graphify-out/graph.json`), считает сообщества (Leiden), «узлы-хабы», неожиданные связи, пишет `GRAPH_REPORT.md`, HTML, wiki, экспорт в Obsidian/Neo4j. Код разбирается локально tree-sitter; документы, PDF и картинки — моделью (моделью самого агента через подагентов или своим API-ключом).

### Как устроено на самом деле

**Конвейер [код]** — `ARCHITECTURE.md` (таблица сверена тестом `tests/test_architecture_doc.py`): `detect()` → `extract()` → `build()` → `cluster()` → анализ → `report.generate()` → `export.to_*()`.

**Разбор кода [код].** tree-sitter по ~37 грамматикам (`pyproject.toml`), извлекатели — в `graphify/extract.py` (8,8 тыс. строк), `graphify/extractors/engine.py` (7,3 тыс.), отдельные модули `graphify/extractors/<lang>.py` (идёт перенос, `extractors/MIGRATION.md`). Порядок добавления языка описан в `ARCHITECTURE.md`: функция `extract_<lang>`, регистрация суффикса в `extract.py`, `detect.py`, `watch.py`, зависимость, фикстура и тесты. Модульность хуже, чем у Graft: регистрация в нескольких местах.

**Модель графа [код].**
- Схема извлечения (`graphify/validate.py`): узел — `id, label, file_type (code|document|paper|image|rationale|concept), source_file, source_location`; ребро — `source, target, relation, confidence, source_file`, опционально `confidence_score`; есть гиперрёбра (связь группы узлов).
- **Метки `EXTRACTED / INFERRED / AMBIGUOUS` [код].** AST-извлекатели ставят только `EXTRACTED` и `INFERRED`. `AMBIGUOUS` ставит **только LLM** при смысловом извлечении — это прописано в промпте (`graphify/llm.py`, «Mark uncertain ones AMBIGUOUS instead of omitting»; `skill.md`: «Never invent an edge. If unsure, use AMBIGUOUS»). Для рёбер есть числовые значения по умолчанию: 1.0 / 0.55 / 0.2 (`graphify/export.py`, `_CONFIDENCE_SCORE_DEFAULTS`). Отчёт показывает доли меток и отдельно список `AMBIGUOUS` для ручной проверки (`graphify/report.py`).
- Узлы-«обоснования»: комментарии `# NOTE:`, `# WHY:`, `# HACK:`, ссылки на ADR/RFC становятся отдельными узлами, связанными с кодом [README; тип `rationale` в `validate.py`].
- **По умолчанию граф неориентированный** (`nx.Graph`, `graphify/build.py`, `build_from_json(..., directed=False)`); направление хранится в атрибутах `_src/_tgt`, а при двух рёбрах между одной парой узлов остаётся последнее. `--directed` даёт `DiGraph`. Мультиграф пока только готовится (`graphify/multigraph_compat.py`).

**Разрешение вызовов [код].** Сильнее, чем у Graft и CodeGraph, по числу языков с типизацией получателя:
- Общий межфайловый проход **отбрасывает все вызовы методов**, а затем по языкам работают отдельные проходы с выводом типа: `_resolve_typescript_member_calls` (внедрение через конструктор), `_resolve_csharp_member_calls` (+ `_resolve_csharp_qualified_calls`), `_resolve_rust_self_member_calls`, Java, Kotlin, Swift, C++, ObjC, Python — все в `graphify/extract.py`.
- Защита «семейств языков» (`_LANG_FAMILY_BY_EXT` в `extract.py`), чёрные списки встроенных функций (например, `_GO_PREDECLARED_FUNCS` в `extractors/go.py`).
- TS/JS: алиасы `tsconfig` (`paths`, `baseUrl`, `extends`), pnpm/npm workspaces, `exports`/`imports` в `package.json`, `.js`→`.ts` — `graphify/extractors/resolution.py`.

**Хранение [код].** `graphify-out/graph.json` (NetworkX node-link), `GRAPH_REPORT.md`, `graph.html`, кэш `graphify-out/cache/` (AST-кэш версионируется по версии пакета и схеме; смысловой кэш — нет, чтобы не платить за LLM повторно: `graphify/cache.py`). `graphify-out/` по умолчанию в `.gitignore`; README предлагает команде явно добавить в git `graph.json` и `GRAPH_REPORT.md`, `graphify hook install` ставит merge-драйвер для `graph.json`.

**Инкрементальное обновление [код].** Кэш по хешу файла (`graphify/cache.py`, `file_hash`), `--update` перерабатывает только изменённые файлы; git-хуки `post-commit` и `post-checkout` пересобирают AST-часть в фоне (`graphify/hooks.py`); после `git pull` надо вручную `graphify update .`; есть `--watch` (`graphify/watch.py`). Удалённые файлы: README предупреждает, что старые узлы могут оставаться, лечится `--force`.

**Инструменты MCP [код]** — `graphify/serve.py`: 10 инструментов — `query_graph` (BFS/DFS с `token_budget`, по умолчанию 2000), `get_node`, `get_neighbors`, `get_community`, `god_nodes`, `graph_stats`, `shortest_path`, `list_prs`, `get_pr_impact`, `triage_prs`; плюс ресурсы (`graphify://report`, `://audit` …). Описания и схемы ≈ 3,7 тыс. символов (≈ 1 тыс. токенов). Можно поднять общий HTTP-сервер на команду с ключом. **Но основной путь — skill**: `graphify/skill.md` ≈ 42 КБ (≈ 10 тыс. токенов) при вызове `/graphify`, плюс подгружаемые по требованию `graphify/skills/claude/references/*.md` (~45 КБ).

**Хуки [код].** Claude Code: `PreToolUse` на `Bash|Grep` и `Read|Glob` — `graphify hook-guard` подталкивает к `graphify query`; режим `--strict` блокирует первое чтение исходника за сессию (`graphify/install.py`, `_claude_pretooluse_hooks`). Git: `post-commit`, `post-checkout`, merge-драйвер (`graphify/hooks.py`).

**Цикл `save-result → reflect` [код]** — `graphify/ingest.py` (`save_query_result`, `OUTCOMES = ("useful", "dead_end", "corrected")`) и `graphify/reflect.py`:
1. После ответа агент вызывает `graphify save-result --question … --answer … --nodes … --outcome useful|dead_end|corrected [--correction …]`. Пишется Markdown с frontmatter в `graphify-out/memory/`; при следующем `--update` эти файлы попадают в граф как документы.
2. `graphify reflect` детерминированно (без LLM) собирает сигналы: каждая ссылка на узел даёт знаковый вес с затуханием (полураспад 30 дней); узел становится «предпочтительным источником» только после ≥ 2 независимых полезных ответов; есть «спорные» (есть и плюс, и минус — решает свежесть), «тупики» и «исправления». Узлы, исчезнувшие из графа, выбрасываются.
3. Результат — `graphify-out/reflections/LESSONS.md` и слой `.graphify_learning.json`; `graphify explain/query` показывают подсказку «Lesson: …» и помечают «code changed — re-verify», если файл изменился с момента записи (сравнение `file_hash`, `reflect.py`).
4. Инструкция агенту — в `graphify/skills/claude/references/query.md`: в начале работы `graphify reflect --if-stale` и чтение `LESSONS.md`, в конце — `save-result` с оценкой.
Оговорка: оценку `outcome` ставит сам агент (или человек), механизм не проверяет её правдивость. Всё лежит в `graphify-out/` — по умолчанию вне git.

**Markdown и PDF [код].**
- Markdown извлекается **без LLM** (`graphify/extractors/markdown.py`): страница → заголовки (вложенность по уровню) → `contains`; ссылки `[text](./x.md)` и `[[wikilinks]]` → `references`; имена в обратных кавычках → ребро «заголовок → символ кода»: `EXTRACTED` для формы с путём (`src/a.py::Widget`), `INFERRED` для голого имени (только при единственном совпадении). Frontmatter читается.
- Смысловое извлечение понятий из документов, PDF, картинок — моделью (`graphify/llm.py`). PDF превращается в текст через `pypdf` (`graphify/detect.py`, `extract_pdf_text`), скан без текстового слоя даёт пустую строку. Есть защита от промпт-инъекций в исходниках (`_INJECTION_SENTINELS` в `llm.py`).

**Последствия правок [код].** Обход соседей и путей по графу; `get_pr_impact` (`graphify/prs.py`, `compute_pr_impact`) считает **затронутые сообщества и число узлов в изменённых файлах**, а не транзитивных вызывающих. Инструмента «связанные тесты» нет.

### Как работает с нашими языками

| Язык | Импорты | Вызовы |
|---|---|---|
| **C#** | `using` с учётом пространств имён (`extractors/csharp.py`, `_resolve_cross_file_csharp_imports`); `.sln/.csproj/.razor/.xaml` | лучший из трёх: `this.M()`, `base.M()`, `Type.M()` → `EXTRACTED`; `field.M()` / параметры / локальные переменные с известным типом → `INFERRED`; неизвестный тип — ребро не ставится |
| **JS/TS** | лучший из трёх: алиасы tsconfig, workspaces, `exports`, `.vue/.svelte/.astro` | свободные функции + методы через внедрение в конструктор |
| **Go** | по `go.mod` | вызовы `pkg.Fn` — да; методы на значениях — отбрасываются (типизации получателя нет) |
| **Rust** | `use` | свободные функции, `Type::f()`, `self.method()` внутри `impl`; прочие методы — отбрасываются |
| Unity-ассеты | `.unity/.prefab/.meta/.asmdef` нет в списке расширений (Unity-YAML лежит в файлах с «своими» расширениями, поэтому не попадает даже в разбор `.yaml` как документа) | — |

### Что полезно для наших слоёв

- **Карта:** метки `EXTRACTED / INFERRED / AMBIGUOUS` + числовой `confidence_score`; разделение «AST ставит только EXTRACTED/INFERRED, модель может поставить AMBIGUOUS»; сообщества и «узлы-хабы» для обзорного уровня карты; `token_budget` в запросах.
- **Журнал работы:** цикл `save-result → reflect` — лучший найденный образец превращения опыта агента в уроки: детерминированно, с затуханием, подтверждением ≥ 2 раза и пометкой «код изменился — перепроверь».
- **Документы:** детерминированный разбор Markdown в граф (заголовки, ссылки, упоминания кода с метками уверенности) — берём почти как есть по идее; PDF → текст → модель.
- **Знания команды:** предложенный путь «коммитить `graph.json` + merge-драйвер» — пример, как делить граф через git.
- **Обоснования:** комментарии `WHY/NOTE/HACK` и ссылки на ADR как узлы.

### Можно ли взять код

Apache-2.0 (+ MIT для ранних частей) — можно. Python; самые полезные части хорошо отделяются: `graphify/reflect.py` (зависит только от `ingest.OUTCOMES` и `paths`), `save_query_result` в `ingest.py`, `extractors/markdown.py`, `extractors/resolution.py` (TS-импорты), `validate.py`. Основные извлекатели (`extract.py`, `engine.py`) — огромные файлы с общим состоянием на уровне модуля, выдирать их тяжело.

### Слабые места

- Граф неориентированный по умолчанию, параллельные рёбра схлопываются — для «кто зависит от кода» это неудобно.
- Нет анализа «кто вызывает транзитивно» по diff и нет поиска связанных тестов; «влияние PR» — это сообщества.
- Go и Rust: вызовы методов на значениях теряются.
- Основной интерфейс — большой skill (~10 тыс. токенов) и CLI, MCP — вторичен.
- Смысловой слой требует модели; `AMBIGUOUS`/`INFERRED` от модели надо проверять.
- Обновление после `git pull` — вручную.
- Лог запросов: README в одном месте говорит «пишется по умолчанию», в другом (таблица переменных) — «выключен, пока не включить». Противоречие в документации, код не проверялся.

### Вердикт: **взять код (точечно) и идеи**

Берём: `reflect.py` + формат `save-result` (как основу журнала работы; код можно портировать), разбор Markdown из `extractors/markdown.py`, схему меток уверенности и `validate.py`, приёмы разрешения TS-импортов из `resolution.py`, узлы-обоснования. Не берём: неориентированный граф, монолитные извлекатели, «влияние = сообщества».

## 4. Greptile (только документация)

### Что это и для чего

Закрытый облачный (или самостоятельно разворачиваемый) AI-ревьюер pull request'ов. Главный результат — комментарии к PR. Источник: `https://www.greptile.com/docs/llms.txt` и страницы из него.

### Как устроено (по документации) [док]

- **Граф кода** (`how-greptile-works/graph-based-codebase-context`): при подключении репозитория разбирает все файлы, строит граф «папки → файлы → функции → вызовы/импорты/переменные» и опрашивает его при ревью: зависимости изменённой функции, места использования, похожие функции (проверка единообразия). Способ разбора и языки не раскрыты («любой язык»).
- **Архитектура** (`system-architecture`): веб, API, приём webhook'ов, воркеры `indexer-chunker` (режет репозиторий на куски), `indexer-summarizer` (LLM-сводки), `reviews` (ревью через LLM), `llmproxy`; оркестрация Hatchet + RabbitMQ; PostgreSQL с **pgvector** (эмбеддинги — «самая большая часть хранилища»); Redis в Kubernetes. То есть на деле: граф + куски + LLM-сводки + векторный поиск.
- **Память и обучение** (`how-greptile-works/memory-and-learning`, `training-the-learning-system`, `nitpicks`): учится по комментариям команды в PR, ответам на свои замечания, реакциям 👍/👎 и по тому, исправлено ли замечание к последнему коммиту; сам выводит правила («контроллеры не должны ходить в БД»), гасит типы замечаний, которые команда игнорирует.
- **Правила и контекст в репозитории** (`code-review/greptile-config`): папка `.greptile/` в любом каталоге — `config.json` (настройки + правила с id и важностью), `rules.md` (правила обычным текстом), `files.json` (какие файлы читать как контекст: схемы, спецификации); настройки каскадно наследуются от корня к подпапкам, правила и контекст суммируются.
- **База знаний** (`how-greptile-works/knowledge-bases`): для каждого репозитория — обзор архитектуры, глоссарий, карта файлов; документ на каждый модуль и сквозной поток (что делает, связи, зоны риска, ключевые файлы); раздел «откаты» — прошлые revert/инциденты. Обновляется сама по изменениям. Доступ через MCP включается **по организациям постепенно** (`mcp-v2/tools`, раздел Knowledge Base Tools), документы помечены `untrustedContent: true` — «кто может закоммитить, тот влияет на текст».
- **MCP** (`mcp-v2/tools`): инструменты про ревью (список PR, комментарии, запуск ревью, поиск по прошлым замечаниям), свои правила (`list/get/search/create_custom_context`), база знаний (4 инструмента), аналитика. Инструментов «найди код / кто вызывает» нет — MCP про результаты ревью.
- **CLI** (`code-review/greptile-cli`): `greptile review` сравнивает ветку с основной, смотрит только закоммиченные изменения; нужен вход в аккаунт или API-ключ — анализ идёт на сервере.
- **T-Rex (бета)** (`code-review/key-features`): пишет целевые тесты под PR и запускает их в песочнице, прикладывает логи/скриншоты к замечанию.
- **Цена** (страница `/pricing`): $30 за место в месяц, включено 50 кредитов на место; ревью сверх — по кредитам.

### Как работает с нашими языками

Заявлено «любой язык»; качество разрешения вызовов для C#, TS, Go, Rust в документации не описано и проверить нельзя. Про Unity-ассеты ничего нет.

### Что полезно для наших слоёв

- **Проверка (после MVP):** сама постановка «ревью изменения с учётом графа»; T-Rex — идея подтверждать замечание запуском теста.
- **Знания проекта:** структура базы знаний (обзор + глоссарий + карта файлов + документ на модуль/поток + раздел «откаты/инциденты»); каскадная папка правил `.greptile/` с `rules.md` и `files.json` — очень близко к нашему «знанию команды в git».
- **Обучение на обратной связи:** счёт «сделано / исправлено / реакции» по типу замечания — похоже на `reflect` у Graphify, но для правил ревью.
- **Безопасность:** пометка сгенерированных документов как недоверенных.

### Можно ли взять код

Нет — закрытый продукт. Самостоятельное развёртывание — Docker Compose/Kubernetes с десятком сервисов и внешним LLM, это не локальная утилита.

### Слабые места

Облако или тяжёлая инфраструктура; закрыто; меньше контроля; стоимость по кредитам; KB-доступ по MCP не у всех.

### Вердикт: **взять идеи**

Берём: каскадные правила в репозитории (`rules.md` + `files.json` по каталогам), структуру базы знаний с разделом инцидентов, пометку недоверенного сгенерированного текста, учёт обратной связи по типам замечаний, идею подтверждения замечаний тестом — для слоя «проверка» после MVP.

## 5. Сквозные вопросы из задачи

### Уровни детализации (L0/L1/L2)

Явных уровней L0/L1/L2 **нет ни у одного** инструмента (поиск по исходникам). Есть аналоги:

| Инструмент | Аналог уровней |
|---|---|
| Graft | `repo_map` (папки, хабы) → `file_api` (сигнатуры без тел) → `find_code` (фрагмент ≤ 8 строк) → `full: true` (полный текст); отдельно LLM-узлы подсистем (`--deep`) |
| CodeGraph | `get_module_summary` → `get_symbol_info` → `get_detailed_symbol`; `get_ai_context` с намерением (`explain/modify/debug/test`) и бюджетом токенов; флаг `compact` |
| Graphify | `GRAPH_REPORT.md` (хабы, сообщества) → wiki на сообщество → `explain` узла → `query` с `token_budget` |
| Greptile | база знаний: индекс → документ на модуль/поток |

Вывод: у нас уровни надо вводить самим; хорошая сетка — «репозиторий/модуль → файл (сигнатуры) → символ (фрагмент) → полный текст», с бюджетом токенов на каждом шаге.

### Метки уверенности связей

| Инструмент | Метки | Кто ставит |
|---|---|---|
| Graft | `lsp_resolved`, `lsp_dispatch`, `extracted`, `inferred` | AST + LSP; неоднозначное — отбрасывается |
| Graphify | `EXTRACTED`, `INFERRED`, `AMBIGUOUS` + `confidence_score` | AST — только первые две; `AMBIGUOUS` — только LLM |
| CodeGraph | нет (только `resolved_by`) | неоднозначное — угадывается по «весу» |
| Greptile | не описано | — |

Вывод: берём шкалу Graphify (три уровня + число), добавляем уровень «подтверждено компилятором/LSP» из Graft, а правило «неоднозначно при AST → не ставить ребро» — из Graft.

### Markdown и PDF

- Graft: документы проекта не индексирует.
- CodeGraph: Markdown — отдельное хранилище кусков по заголовкам с эмбеддингами, индексация вручную по файлу; связь с кодом только через проверку идентификаторов. PDF нет.
- Graphify: Markdown — детерминированно в тот же граф (заголовки, ссылки, упоминания кода с метками); PDF — `pypdf` → текст → модель.
- Greptile: сам пишет Markdown-базу знаний; свои файлы подключаются через `files.json`.

Вывод: основа для слоя «документы» — подход Graphify к Markdown; PDF — извлечение текста + смысловой проход моделью с метками `INFERRED/AMBIGUOUS`.

### Расход контекста на описания MCP-инструментов

| Инструмент | Число инструментов | Описания + схемы (оценка по строкам в исходниках) | Прочее |
|---|---|---|---|
| Graft | 6 | ≈ 2,5 тыс. символов (≈ 0,7 тыс. токенов) | `instructions` ≤ 1 тыс. символов; SKILL.md ≈ 9 КБ; подмешивание результатов по хукам на каждый запрос |
| CodeGraph | 42 (профили 8/17/14) | ≈ 26 тыс. символов (≈ 6–7 тыс. токенов) | правила агенту — во внешнем репозитории |
| Graphify | 10 | ≈ 3,7 тыс. символов (≈ 1 тыс. токенов) | skill ≈ 42 КБ (≈ 10 тыс. токенов) при вызове + `references/` по требованию |
| Greptile | десятки (про ревью и аналитику) | не мерилось | — |

Оценка токенов грубая (символы / 4). Вывод: держать 5–8 инструментов с короткими описаниями, использовать `instructions` в MCP (Graft) и профили (CodeGraph), тяжёлые инструкции — в подгружаемые файлы skill (Graphify `references/`).

### Unity (сцены, префабы)

Ни один инструмент не читает `.unity`, `.prefab`, `.meta`, `.asmdef` и не знает о методах, которые вызывает движок (`Awake`, `Update`, `OnTriggerEnter`). Для нас это собственная разработка: модуль, который связывает GUID из `.meta` со скриптами, а компоненты в сценах/префабах — с классами.

## 7. Главные выводы

1. Готового решения для нашего стека нет: ни один инструмент не понимает Unity-сцены и префабы, а C# и Rust у Graft и CodeGraph разбираются слабо. Лучший разбор C# и TS-импортов — у Graphify.
2. Модель модулей языков берём у Graft: «глубокий» ручной извлекатель для главных языков + общий извлекатель на `tags.scm` для остальных. Это самый дешёвый путь к расширяемости силами сообщества.
3. Правило разрешения связей: не угадывать неоднозначное, помечать уверенность (`EXTRACTED / INFERRED / AMBIGUOUS` + «подтверждено LSP»). CodeGraph показывает, чем плохо угадывание без меток.
4. Для последствий правок объединяем `blast` Graft (по diff, до символа, сигнал по тестам) и `get_edit_context` + `find_related_tests` CodeGraph.
5. Для журнала работы основа — цикл `save-result → reflect` Graphify; формат записи — по схеме памяти CodeGraph (двойное время, вид, источник), но с привязкой к стабильному ключу символа и хранением в git.
6. Для документов — детерминированный разбор Markdown Graphify в общий граф; PDF — текст + модель с метками.
7. Для знаний команды — каскадные правила Greptile (`rules.md` + `files.json` по каталогам) и структура базы знаний с разделом инцидентов.
8. Расход контекста: 5–8 коротких инструментов + `instructions` в MCP + лёгкий skill с подгружаемыми частями. 42 инструмента CodeGraph (≈ 6–7 тыс. токенов) — пример того, чего избегать.
9. Код напрямую реально взять из Graft (MIT, TS) и Graphify (Apache-2.0, Python: `reflect.py`, `markdown.py`, `resolution.py`) — выбор зависит от языка нашего плагина; CodeGraph — только идеи.
