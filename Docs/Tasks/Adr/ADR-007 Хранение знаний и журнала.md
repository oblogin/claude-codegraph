# ADR-007 Хранение знаний и журнала

> **Решение:** знания проекта и глобальная база хранятся «страницами тем» — Markdown-страница на модуль кода или тему, внутри факты-строки с ID, привязкой к символу и хэшем; крупные решения — отдельными файлами; SQLite — только производный индекс; журнал работы — SQLite локально.
> **Почему:** реальный объём знаний — сотни и тысячи фактов, а свалку создаёт отсутствие правил жизни записи; страница модуля даёт агенту и человеку весь контекст одним чтением и в десятки раз меньше файлов, чем карточки, а схема «база + выгрузка» уже провалилась у Beads.
> **Следствия:** нужен строгий парсер строк факта с тестами, `merge=union` и проверка `lint` («садовник»); индекс считает «под сомнением» и затухание сам и ничего вычисляемого в git не пишет; интерфейс ADR-003 и граф ADR по [[F03-06 Архитектура графа и конвейер индексации]] опираются на стабильные ключи символов.

## Контекст

Вопрос [[F03-03 Хранение индекса и знаний]] и опасение пользователя: при десятках тысяч записей Markdown превратится в свалку, знания устаревают, их надо дополнять и править. Исследование — [[F03-05 Форматы хранения знаний и их жизнь]], отчёт `Docs/Research/09-knowledge-storage.md` (варианты A «карточки», B «страницы тем», C «база и выгрузка»). Требования: ADR-001 (разделы 4, 5, 5а), [[F-07 Знания проекта]], [[F-14 Глобальная база знаний]]. Хранение индекса графа кода — в ADR по [[F03-06 Архитектура графа и конвейер индексации]].

## Решение

**1. Три носителя.**

| Что | Где | Формат | В git |
|---|---|---|---|
| Журнал работы | `~/.codegraph/journal/<id проекта>.db` (путь только ASCII; id проекта — по нормализованному `origin`) | SQLite, события «только добавлять» | нет |
| Знания проекта | `Docs/Knowledge/` в репозитории проекта | страницы тем + файлы решений | да |
| Глобальная база | `~/.codegraph/global/` | те же страницы, темы по технологиям (`unity/editor.md`, `go/build.md`) | локальный git в папке для истории, без удалённого |
| Подключённые базы коллег | `~/.codegraph/attached/<имя>/` | тот же формат | только чтение |
| Индекс | `.codegraph/index.db` в проекте, `~/.codegraph/global.db` | SQLite + FTS5, производный | нет (`.gitignore`) |

**2. Страница темы.** Одна страница на модуль кода (папку, `scope:` во frontmatter) или на сквозную тему (`topics/…`). Разделы: «Правила», «Тупики», «Решения», «Рецепты», «История». Факт — одна строка списка:
```
- [dead-end] `OverlapSphereNonAlloc` с буфером 8 теряет цели в толпе — берём 64. <!-- id:m7q2x8d4k1 code:csharp:Assets/Scripts/Combat/Targeting.cs#Targeting.FindTargets h:3fa9c1 v:2026-10-02 -->
```
- Служебные поля — в HTML-комментарии в конце строки: при просмотре не видны, в git и для парсера есть.
- `id` — 10 символов base32 со случайной частью, глобально уникален (базы разных людей сливаются).
- `code` — стабильный ключ символа из графа; `h` — хэш тела символа на момент проверки; `v` — дата проверки; `from` — происхождение (проект и коммит или чья база).
- Место факта выбирается без модели: по модулю символа, к которому он привязан; без привязки — сквозная тема по метке.
- Крупные решения с обсуждением — отдельные файлы `Docs/Knowledge/decisions/…`, на странице — строка-ссылка.
- Оглавление `MEMORY.md` генерируется индексом и **не коммитится** (нет конфликтов; для старта сессии оно всё равно берётся из индекса).

**3. Жизнь факта** (отчёт 09, §6).
- Состояния: кандидат (журнал) → действует → под сомнением (вычисляется) → перепроверено; заменено; отозвано; в архиве.
- Автоматика только добавляет кандидатов в журнал; в знания — только явным действием агента или человека. Ничего не удаляется автоматически.
- Вычисляемое (под сомнением, счётчики, затухание, оценки полезности) живёт только в индексе.
- Сначала дописать существующую страницу, потом создать новую; перед записью — подсказка «похоже на …».
- Противоречие исправляется в источнике: старая строка уходит в «Историю» со ссылкой на преемника.
- Затухание влияет только на ранжирование.
- Порог записи: не записываем то, что быстро читается из кода, общие знания о языке, разовые детали задачи.

**4. Слияние.**
- В git проекта: `.gitattributes` — `Docs/Knowledge/**/*.md merge=union`; две правки одного факта дают две строки с одним `id` — их ловит `lint`.
- Глобальная база: подключение — указать папку (только чтение, в выдаче видно происхождение); слияние — по `id`, затем поиск похожих, затем выбор при конфликте; выгрузка — страницы только с отмеченными фактами.
- Подъём «проект → глобально» — копия строки с обобщёнными путями и `from:`.

**5. «Садовник» (`codegraph lint`).**
- Без модели, автоматически после индексации: дубли `id`, два текста у одного `id`, битые ссылки и привязки к исчезнувшим символам, страницы сверх лимита (по умолчанию 400 строк) и оглавление сверх бюджета, давние «под сомнением».
- С моделью — только по явной команде: предложить слить похожие факты, переписать страницу. В конце сессии — только короткое напоминание, если `lint` что-то нашёл.

**6. `claude-tasks`.** ADR и журналы задач индексируются как источник знаний только для чтения, не копируются.

**7. Когда пересмотреть.** Если глобальная база перевалит за 20–50 тыс. фактов или `lint` и поиск станут медленными — только глобальную базу перевести на SQLite как источник правды с Markdown-выгрузкой; формат знаний проекта не меняется.

**Непроверенные допущения.**
- `merge=union` на практике не портит страницы при одновременных правках — проверить тестом слияния в реализации [[F-07 Знания проекта]].
- Строгий синтаксис строки факта не путается с обычным Markdown — тесты парсера в [[F-07 Знания проекта]].
- Лимит 400 строк на страницу разумен — уточнить на реальных данных.

## Отвергнутые варианты

- **A «карточки» (файл на запись)** — проще и почти без конфликтов, но тысячи файлов, контекст модуля размазан, дубли создать легче; остаётся для крупных решений.
- **C «SQLite — правда, в git — JSONL»** — два источника правды, надгробия, свой драйвер слияния; Beads отказался от этой схемы, выбросив ~27 тыс. строк; человек не правит руками.
- **Dolt и графовая БД со временем (Graphiti)** — тяжёлые зависимости, каждое добавление через модель, человеку не прочитать.
- **Коммит `MEMORY.md` и вычисляемых полей** — шум и конфликты в git.
- **Скрытая папка `.codegraph/knowledge/`** для знаний проекта — знания должны быть на виду рядом с `Docs/Tasks/`.
