# ADR-004 Своё ядро на Rust

> **Решение:** ядро claude-codegraph пишем сами на Rust одним бинарником (CLI, MCP-сервер по stdio и обработчики хуков), взяв за основу каркас нашей ue-xray (`rusqlite` со встроенным SQLite и FTS5, `rmcp`, `tree-sitter`, `rayon`); готовые движки ставятся рядом только как эталон для сравнения.
> **Почему:** ни один готовый движок не читает Unity и не держит память, привязанную к стабильным ключам; каркас ue-xray уже работает под Windows с Claude Code, а Rust даёт скорость разбора, родной tree-sitter и установку без Node, Python и Docker.
> **Следствия:** архитектура графа ([[F03-06 Архитектура графа и конвейер индексации]]) проектируется под Rust-воркспейс; на машине разработки нужен Rust (MSVC уже установлен); хуки — подкоманды того же бинарника; заимствования из чужих проектов учитываются в `THIRD_PARTY.md`.

## Контекст

Вопросы [[F03-01 Своё ядро или готовый движок]] и [[F03-02 Язык ядра и способ поставки]]. Вход: ADR-001 (раздел 9 — кандидаты на готовый код), ADR-002, отчёты `Docs/Research/04-market.md` (§2.1 `colbymchenry/codegraph`, §2.2 CBM), `08-ue-xray.md`.

Кандидаты в готовый движок:
- **CBM** (`DeusData/codebase-memory-mcp`, C, MIT) — сильный разбор C#/Go/Rust, но C-монолит, Unity не читает, память и наши метки связей пришлось бы встраивать в чужую кодовую базу.
- **`colbymchenry/codegraph`** (TS, MIT) — хорошие идеи (`explore`, свежесть, неразрешённые ссылки), но ядро на Node, Unity нет, телеметрия.
- **ue-xray** (наш, Rust, MIT) — заточен под Unreal (121 таблица, узлы только для `UFUNCTION`), но каркас (бинарник, SQLite, MCP, tree-sitter, параллельный разбор) переносится почти один в один.

Пользователь: прототип закрытый; брать можно любой код; в перспективе — универсальный парсер на Rust; решения — за лидом.

## Решение

**Своё ядро.** Пишем сами, по модели графа из ADR [[F03-06 Архитектура графа и конвейер индексации]]. Из ue-xray берём кодом каркас: слой MCP (`crates/xray-mcp`), работу с SQLite, рекурсивный SQL последствий (`impact.rs`), обход tree-sitter с картой локальных типов (`crates/xray-cpp/src/call_graph.rs`), крейт `xray-vault` (для знаний, после исправлений аудита M8–M11). Модель графа, идентичность узлов и разрешение связей — новые (см. уроки ue-xray: целочисленные id, разрешение в момент вставки, таблица на каждый вид ассета — не повторять).

**Готовые движки** — только эталон: CBM и `colbymchenry/codegraph` подключаются к тест-раннеру [[F02-02 Скрипт прогона набора проверок]] адаптерами, чтобы сравнить полноту и точность с нашим.

**Язык и поставка.**
- Rust (версия как в ue-xray, 1.93+), воркспейс крейтов: ядро графа, модули языков, Unity, хранилище, MCP, CLI.
- Один бинарник `codegraph`: `codegraph index`, `codegraph query …`, `codegraph mcp` (stdio), `codegraph hook <событие>` — хуки Claude Code вызывают его напрямую (старт — миллисекунды, Node не нужен).
- Плагин Claude Code — папка `plugin/` с `.claude-plugin/plugin.json`, `.mcp.json`, `hooks/hooks.json`, скиллами; бинарник лежит в `plugin/bin/`.
- Прототип: сборка из исходников (`cargo build --release`) на машине пользователя. Публикация ([[F-13 Публикация для сообщества]]): готовые сборки под Windows, macOS, Linux.
- Грамматики tree-sitter (C#, TS/TSX/JS, Go, Rust, Markdown) вкомпилированы; Unity-YAML — свой потоковый разбор по заголовкам документов (ADR-001, раздел 3).
- Локальная модель (ADR-002) — HTTP к Ollama или LM Studio; своих нативных частей модели нет.
- Тест-раннер набора проверок — тоже крейт воркспейса, чтобы тесты F02-03 шли через `cargo test`.

**Учёт заимствований.** Код из ue-xray — наш (MIT), но всё равно отмечается в `THIRD_PARTY.md` с коммитом, чтобы было видно происхождение. Чужой код — по правилу ADR-001.

## Отвергнутые варианты

- **CBM как основа** — чужой C-монолит; Unity, память и метки связей пришлось бы встраивать в него; развитие зависит от автора.
- **`colbymchenry/codegraph` как основа** — Node-ядро, телеметрия, нет Unity; переписали бы больше, чем взяли.
- **TypeScript/Node как язык ядра** (как `claude-tasks`) — проще старт без установки Rust, но медленнее разбор больших проектов, нативные модули (`better-sqlite3`, tree-sitter) капризны на Windows, а WASM-вариант tree-sitter медленнее; пользователь сам склоняется к Rust.
- **Python** — нужен интерпретатор у пользователя, медленнее, сложнее поставка.
- **Go** — хороший вариант для одного бинарника, но tree-sitter через cgo, и нет готового каркаса, как у ue-xray.
- **Форк ue-xray целиком** — потащили бы Unreal-специфику (121 таблица, 127 инструментов) и её долги; берём только каркас.
