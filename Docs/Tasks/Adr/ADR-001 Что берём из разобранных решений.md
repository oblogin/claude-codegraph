# ADR-001 Что берём из разобранных решений

> **Решение:** систему собираем по слоям из приёмов, перечисленных ниже; своё пишем там, где аналогов нет (сцены и префабы Unity, знания команды в git); готовый код берём только из проектов под MIT, Apache-2.0 или BSD и только отделяемыми кусками.
> **Почему:** ни одно разобранное решение не закрывает наш стек целиком: сцены и префабы Unity не читает никто, общих знаний команды в git нет ни у кого, а лучшие приёмы разбросаны по разным проектам и лицензиям.
> **Следствия:** задачи F03-01…F03-04 и фичи F-04…F-10 берут приёмы из этого списка без повторного исследования, кандидаты на готовый код и движки прогоняются на наборе проверок F-02, а непроверенные допущения закрываются в задачах, названных в конце раздела «Решение».

## Контекст

**Что решаем.** Пять отчётов исследования (F01-01…F01-05) дали десятки приёмов из нескольких десятков проектов, и часть из них отчёты оценивают по-разному. Нужен один согласованный список: какой приём берём, в какой слой и фичу, откуда он и берём ли код или только идею.

**Принцип отбора.** Берём только то, что закрывает четыре проблемы пользователя:
1. агент изучает проект с нуля в каждой сессии → карта кода;
2. агент ломает зависимости, которых не видит → последствия правок и Unity;
3. забытые решения и повторные тупики → журнал работы, знания проекта, документы;
4. правки не проверяются перед слиянием → проверка изменений (после MVP).

**Ограничения** (из [[E-01 Исследование и архитектура]] и вводных пользователя):
- это плагин Claude Code, а не свой агент и не оркестратор;
- небольшая команда; стек — Unity (C#, сцены и префабы — приоритет), браузерные игры (JS/TS), Go, Rust; Unreal отложен;
- MVP-1 — карта кода, последствия правок, Unity; MVP-2 — журнал работы (локально), знания проекта (Markdown в git), документы (Markdown, PDF); проверка изменений — после MVP;
- 5–8 инструментов MCP;
- код не уходит в чужие облака, кроме запросов к самой модели;
- архитектура — для сообщества: языки и форматы подключаются модулями.

**Что этот ADR не решает.** Своё ядро или готовый движок — [[F03-01 Своё ядро или готовый движок]]. Язык ядра и поставка — [[F03-02 Язык ядра и способ поставки]]. Формат и место хранения — [[F03-03 Хранение индекса и знаний]]. Точный список инструментов и хуков — [[F03-04 Интерфейс для агента]]. Здесь для них собран вход: приёмы, кандидаты на готовый код с лицензиями и рисками, противоречия и допущения. Готовый код пользователя (X-Ray Copilot и другие наработки) в отчётах не разбирался: его сравнивают с таблицей кандидатов в F03-01.

**Источники и обозначения.** Отчёты лежат в `Docs/Research/`. В таблицах ссылка на отчёт — его номер и раздел:

**Правило заимствования кода** (изменено 2026-09-29 по решению пользователя).
- **Прототип и MVP** — инструмент закрытый, им пользуется только пользователь. Чужой код можно брать под любой лицензией, в том числе AGPL, GPL, ELv2, PolyForm Noncommercial: цель — быстро проверить, что система работает. Пометки «код» и «идея» в таблицах ниже — это советы, где выгоднее взять код, а где проще написать своё.
- **Учёт обязателен:** каждое заимствование записывается в `THIRD_PARTY.md` (проект, файл, коммит, лицензия, куда взято). Это список того, что придётся переписать.
- **Перед публикацией** ([[F-13 Публикация для сообщества]]) вся взятая логика из `THIRD_PARTY.md` переписывается своей; зависимостями остаются только базовые библиотеки (tree-sitter, SQLite, языковые серверы, Ollama или LM Studio) с разрешительными лицензиями.
- Риск: PolyForm Noncommercial запрещает коммерческое использование даже внутри компании; если инструмент применяется в коммерческой разработке, код GitNexus лучше не брать и в прототипе.
- Готовые движки целиком (CBM, `colbymchenry/codegraph`) можно поставить рядом как эталон для сравнения на [[F-02 Набор проверок на наших проектах]].

## Решение

Колонка «Как» в таблицах: **код** — берём файл или функцию (с указанием источника); **идея** — пишем своё по образцу; **своё** — аналогов нет. Колонка «Фича» — куда приём идёт в первую очередь.

## Отвергнутые варианты

**Движки целиком**
- **agentmemory как движок журнала** — сервер живёт внутри iii-engine под ELv2; на Windows движок ставится вручную или через Docker / WSL2; демон с 4 портами; без ключа LLM почти всё «умное» выключено (02).
- **claude-mem как движок журнала** — нужны Bun, по умолчанию Python / uv для Chroma и bash-хуки; «наблюдатель» тратит подписку пользователя; телеметрия включена; командная синхронизация — закрытая платная часть (02).
- **OpenViking** — код под AGPL-3.0; как движок тяжёл: Python-сервер, обязательные эмбеддинги и LLM, свой векторный движок на C++ (02). Берём только идеи.
- **CodeGraph (`codegraph-ai`) кодом** — угадывает связи по глобальной карте имён без меток уверенности; хранит всё в `~/.codegraph` вне git; привязывает заметки к числовым id, которые меняются; хук автоматически разрешает правки; 42 инструмента ≈ 6–7 тыс. токенов; тянет RocksDB и ONNX Runtime; телеметрия по умолчанию (01 §2). Берём только идеи.
- **Greptile** — закрытый облачный продукт, код уходит на их сервер (01 §4). Только идеи.
- **Unity CLI как основа MVP-1** — закрытый код, бета, нет схемы ответа, «живой» режим требует открытого редактора Unity 6+ (05 §2.5). Остаётся эталоном для сверки.
- **Unity MCP-серверы и мосты в редактор** (CoplayDev, IvanMurzak, CoderGamester, `verysleepylemon/unity-mcp` как выгрузка) — нужен открытый редактор, задуманы для правок, а не для графа; свой мост в редактор попадает под п. 17.2 (gg) условий Unity (05 §3.2–3.3, 04 §3.6).

**Код с неподходящей лицензией**
- **GitNexus** — PolyForm Noncommercial: запрет на коммерческое использование перешёл бы на наш продукт (04 §2.3).
- **Приложение Serena** — GPL-3.0 (берём только SolidLSP под MIT) (04 §2.5).
- **basic-memory** — AGPL-3.0 (04 §1.5).
- **iii-engine** (движок agentmemory) — ELv2 (02).

**Заброшенное и тяжёлое**
- **`github/stack-graphs`** — в архиве с 2025-09-09 (04 §1.6).
- **`tree-sitter-graph`** — не развивается с 2024-12 (04 §1.6).
- **Kuzu** — в архиве с 2025-10; форк LadybugDB молодой и с нативным модулем (04 §4.3). Графовые БД (Neo4j, Memgraph, FalkorDB) для локального плагина не нужны: лидеры обходятся SQLite.
- **Dolt** для знаний — тяжёлая зависимость (04 §2.7, §4.3).
- **Glean** — рассчитан на масштаб Meta, слишком тяжёл (04 §1.6).
- **claude-context (Milvus / Zilliz Cloud)** — нужна внешняя база или облако (04 §3.3).
- **LanceDB** — у Continue были проблемы с нативным модулем и AVX2 (04 §3.4, §4.3).
- **EventStore Q00 кодом** (3100 строк про гонки процессов) и **пакет проверок `boundary/`** (~15 тыс. строк) — слишком сложно и связано с Q00 (03 Q2a, Q3).
- **Конвейер `commit_reviewed` razzant кодом** — связан с биллингом и маршрутизацией моделей; три модели на каждый коммит — дорого (03 R1).
- **Сторонние парсеры YAML Unity как зависимости** — маленькие и узкие, свой индексатор дешевле (05 §3.1).

**Приёмы, которые не берём**
- Разрешение вызовов угадыванием по имени с выбором «самого сложного» символа (CodeGraph `watcher.rs`) — ложные рёбра, которые нельзя отличить (01 §2).
- Неориентированный граф по умолчанию и «влияние PR = затронутые сообщества» (Graphify) — не отвечает на «кто зависит от кода» (01 §3).
- Хук с `permissionDecision: "allow"` (CodeGraph, claude-mem) — обходит разрешения Claude Code (01 §2, 02).
- Мост, который перезаписывает `MEMORY.md` Claude Code памятью всех проектов (agentmemory `claude-bridge`) (02).
- `CLAUDE.md` по папкам с таблицей ID из личной базы в git (claude-mem) — чужие ID бессмысленны и дают конфликты (02).
- Подмешивание памяти на каждый запрос или вызов инструмента по умолчанию (agentmemory, OpenViking) — расход лимитов (02, К5).
- Коммит графа в git в MVP (CBM `merge=ours`, Graphify `graph.json`) — рост истории до гигабайт (04 §2.2, К6).
- Общая память через общий сервер или P2P с правилом «последняя запись побеждает» (agentmemory `team-share`, `mesh`; ai-memory) — наша цель — знания в git репозитория (02, 04 §2.8).
- Один большой JSON или JSONL на все знания (agentmemory `state.json`, ранний Beads) — не сливается нормально (02, 04 §2.7).
- Замена версий записей по сходству слов (Jaccard) без подтверждения — ложные замены (02).
- Дедупликация по хэшу в памяти процесса на 5 минут (agentmemory) — пропускает изменённый файл и сбрасывается при перезапуске (02).
- Сортировка журнала по времени с UUID при равенстве (Q00) — порядок случаен (03 Q3).
- Обязательные описания модулей и папок моделью (Graft `--deep`, OpenViking L1) в MVP — стоят токенов и не обновляются сами; L0/L1 делаем детерминированными (01 §1, 02).
- Большой skill как основной интерфейс (Graphify ≈ 10 тыс. токенов) и 42 инструмента (CodeGraph) — расход контекста (01 §5).
- Телеметрия по умолчанию (Graft, codegraph, CodeGraph, claude-mem) — противоречит принципу «код не уходит наружу».
- Жюри из моделей разных вендоров как обязательная часть (Q00 `reviewer_independence`) — код уходит в ещё одно облако; только как необязательная метка (03 Q1b).
- Выполнение кода в песочнице для подтверждения замечаний (Greptile T-Rex) — в F-09 «Не входит» (01 §4).
- Оценка неясности задачи (Q00 `ambiguity.py`) — не про наш плагин; идея для `claude-tasks` (03).
- Бенчмарки памяти переписки (LongMemEval, LoCoMo) и звёзды GitHub как критерий выбора — меряют не код и не качество (02, 04).
